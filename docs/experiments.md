# Эксперименты: интенсивность, перенос, смещение, tracking

Baseline-модели, на которых всё ниже обучается и оценивается — см. `baselines.md`.

## Чувствительность к интенсивности атаки (M9)

```bash
uv run netstream-ml evaluate intensity data/v1 --window 5
```

Все три baseline'а из `baselines.md` оцениваются на «типичном» прогоне каждого сценария — но `lab/run.sh` даёт каждому flood/scan/tunnel-сценарию параметр `--rate`, и кампания `v1.yaml` уже гоняет несколько сценариев на разных `rate` (`syn_flood` на 200/1000/5000 pps, `port_scan` на 50/500/1000 pps/с, `dns_tunnel` на 10/20/40 запросов/с, и т. д.) — то есть в уже накопленных данных лаборатории есть реальная вариация интенсивности, просто раньше не было способа привязать окно признаков обратно к параметрам породившего его запуска. Для этого `features build` теперь прокидывает `run_id` через агрегацию (тем же правилом «последняя запись в окне», что и для `label`/`scenario`/`split`), а `netstream_ml.intensity` соединяет его с `rate` из `labels.params`.

Модели обучаются как обычно на `train`; recall считается по `rate`-группам на **отложенных** строках (`val`+`test`) — модель не видела именно эти окна на обучении, даже если видела другие окна того же `rate` в train.

**Результат на реальном датасете** (те же 92+ запуска лаборатории, что и в `baselines.md`). Самое чёткое наблюдение: у Random Forest recall остаётся высоким почти на всех группах, где вообще есть отложенные данные (`syn_flood` 1.0/0.944 на 200/1000 pps, `slow_scan` 1.0, `slowloris` 1.0 на обеих интенсивностях, `dns_tunnel` 1.0 на 10 и 40 запросов/с) — в отличие от порогов и Isolation Forest, у которых recall куда более рвано зависит от конкретного сценария и `rate` (Isolation Forest, например, почти везде 0.0, кроме `dns_tunnel` и нескольких «громких» вариантов — то же самое ограничение контаминации 0.01, что и в `baselines.md`, здесь просто видно ещё нагляднее). Есть и контринтуитивные строки — например, `port_scan` у Random Forest: recall 1.0 при `rate=500`, но 0.5 при `rate=1000` (более быстрое сканирование поймано хуже, не лучше) — и `c2_beacon` у порогов: 0.5 при `rate=1`, но 0.0 при `rate=5`.

**Ограничение честности, а не результата**: большинство `rate`-групп в отложенной выборке — это 2–18 строк (один-два прогона лаборатории на комбинацию сценарий+`rate`), а для части комбинаций (`syn_flood` на 5000 pps, например) все прогоны целиком попали в `train`, и в отложенной выборке эта интенсивность вообще отсутствует. На таком размере группы «recall упал с 1.0 до 0.5» и «recall упал с 1.0 до 0.0» неотличимы от шума одного-двух прогонов — контринтуитивные строки выше стоит читать как «требует больше прогонов для проверки», а не как надёжно установленный эффект. Настоящая проверка чувствительности к интенсивности потребовала бы отдельной кампании с несколькими повторами на каждый `rate` для каждого сценария, а не анализа уже существующих данных постфактум — это и есть логичное следующее действие, если чувствительность к интенсивности станет отдельным вопросом дальнейшей работы.

## Перенос на внешний датасет (M10)

```bash
uv run netstream-ml evaluate transfer data/v1 <cic-flowmeter>.csv --window 5
```

Все результаты выше проверяют одно и то же: обобщается ли модель на атаки, которых не видела *в обучении*, но всё ещё внутри одной и той же лаборатории — тот же eBPF-агент, тот же формат признаков, те же фоновые хосты. M10 — другой вопрос: что случится с тем же детектором на трафике совсем из другого источника, собранном другим инструментом (`netstream_ml.external`, датасеты CIC-IDS2017/CIC-DDoS2019).

CICFlowMeter — не наш агент: он агрегирует по одному потоку (5-tuple), а не по (`src_ip`, окно), и не заглядывает в полезную нагрузку DNS вообще. Из-за этого большая часть `FEATURE_COLUMNS` не восстанавливается из его CSV в принципе, а не потому что не хватило времени на парсинг:

- все `dns_*` — в датасете нет разбора DNS-запросов;
- `receive_ratio` — у нас это доля пакетов окна, адресованных источнику *извне* его собственных потоков; у CICFlowMeter fwd/bwd — это направление внутри одного и того же потока, другая ось;
- `synack_ratio` — нет отдельного счётчика SYN+ACK, только раздельные SYN/ACK;
- `aggregated_ratio` — GRO/GSO-агрегация пакетов существует только на уровне eBPF-агента;
- все `size_*_ratio` — CICFlowMeter даёt min/max/mean/std длины пакета на поток, а не гистограмму по отдельным пакетам, бины из этого не восстановить даже приближённо.

`RECONSTRUCTABLE_FEATURES` — то, что осталось (9 из 24): счётчики пакетов/байт/потоков, разброс по destination, `syn_ratio`/`rst_ratio`, среднее и стандартное отклонение межпакетного интервала (пересчитанные из **пер-потокового** mean/std тем же способом, каким `WindowAccumulator` объединяет статистику нескольких записей в одно окно — иначе усреднение по потокам внутри окна было бы смещённым). `evaluate transfer` переобучает все три baseline'а на лабораторных данных, урезанных до этого же подмножества, и оценивает на:

- `lab_test_same_features` — тот же тестовый сплит лаборатории, что и везде выше, но **только** на урезанном наборе признаков — чтобы отделить «цена урезания признаков» от «цена переноса на другой источник данных»;
- `external` — тот же обученный детектор на признаках, посчитанных из внешнего CSV.

**Результат на реальном датасете.** Внешний файл — `UDPLag.csv` из CIC-DDoS2019 (`01-12`, тренировочный день), самый маленький файл в архиве (1176 окон после агрегации: 645 `benign`, 426 `udp-lag`, 105 `webddos`). Падение резкое и по recall, и по precision у всех трёх baseline'ов:

| | lab test (урезанные признаки) | external |
|---|---|---|
| threshold | F1 0.603 (precision 0.636, recall 0.574) | F1 0.070 (precision 0.113, recall 0.051, **FPR 0.329**) |
| Isolation Forest | F1 0.063 (recall 0.033) | F1 0.033 (recall 0.017) |
| Random Forest | F1 0.949 (precision 0.982, recall 0.918) | F1 0.256 (precision 0.330, recall 0.209, **FPR 0.349**) |

Random Forest остаётся лучшим из трёх и на внешних данных, но падение с F1 0.949 до 0.256 — это не «немного хуже», а «почти не работает»: FPR 0.349 означает, что треть обычного фонового трафика чужой сети размечается как атака. По сценариям видно и почему: recall на `udp-lag` у леса — 0.204, на `webddos` — 0.229, оба намного ниже, чем на любом сценарии из раздела «Чувствительность к интенсивности атаки» выше, даже на самых тихих его вариантах.

**Первая гипотеза (уточняется ниже вторым и третьим прогоном).** UDPLag — атака поверх UDP, у неё нет TCP-флагов, а 2 из 9 восстановимых признаков (`syn_ratio`, `rst_ratio`) на UDP-трафике тождественно равны нулю что для атаки, что для фона — правдоподобная (но, как окажется ниже, не полная) причина низкого recall. Высокий FPR на `benign`-строках внешнего датасета — это, судя по всему, отдельный эффект: «нормальный» трафик другой сети (другие IP-диапазоны, другое распределение `unique_dst_ports`/`flows_count`) просто не похож на «нормальный» трафик лаборатории, на котором калибровались пороги. Это именно тот разрыв между «обобщение на новую атаку внутри своей же лаборатории» (F1 0.983 на полном наборе признаков в `baselines.md`; recall 0.9–1.0 почти на всех rate-группах Random Forest выше) и «перенос на чужую сеть и чужой инструмент сбора» — второе оказалось на порядок сложнее, и один прогон на одном файле уже это ясно показывает.

**Проверка гипотезы: второй прогон, `Syn.csv` (TCP SYN-flood, тот же день CIC-DDoS2019).** Всего 179 окон после агрегации (87 `benign`, 92 `syn`) — заметно меньше, чем на `UDPLag.csv`, потому что почти весь поток шёл от одного-двух атакующих адресов; читать эти числа стоит с той же осторожностью, что и малые `rate`-группы в разделе выше.

| | external (UDPLag, UDP) | external (Syn, TCP) |
|---|---|---|
| threshold | F1 0.070 (recall 0.051, FPR 0.329) | F1 0.568 (recall 0.522, FPR 0.333) |
| Isolation Forest | F1 0.033 (recall 0.017) | F1 0.467 (recall 0.304) |
| Random Forest | F1 0.256 (recall 0.209, FPR 0.349) | F1 0.543 (recall 0.511, FPR 0.391) |

Recall всех трёх baseline'ов на TCP-атаке в 3–10 раз выше, чем на UDP-атаке (Isolation Forest — 0.304 против 0.017), что на первый взгляд подтверждает гипотезу про `syn_ratio`. При этом FPR на `benign`-окнах остался почти таким же высоким (0.33–0.39 против 0.33–0.35 на UDPLag) — то есть ложные срабатывания на фоновом трафике чужой сети объясняются не спецификой атаки, а именно тем, что «нормальный» трафик внешней сети не похож на «нормальный» трафик лаборатории. Возможность детектировать атаку и умение не путать чужой benign со своим — это два разных провала, и перенос признаков лечит только первый.

**Третий прогон, `DrDoS_LDAP.csv` (UDP-amplification, тот же день).** 636 окон (398 `benign`, 238 `drdos_ldap`) — этот прогон опровергает исходную формулировку гипотезы «дело в протоколе»:

| | UDPLag (UDP, «тихая» атака) | Syn (TCP-flood) | DrDoS_LDAP (UDP-amplification) |
|---|---|---|---|
| threshold | F1 0.070 (recall 0.051) | F1 0.568 (recall 0.522) | F1 0.541 (recall 0.508) |
| Isolation Forest | F1 0.033 (recall 0.017) | F1 0.467 (recall 0.304) | F1 0.667 (recall 0.500) |
| Random Forest | F1 0.256 (recall 0.209) | F1 0.543 (recall 0.511) | F1 0.498 (recall 0.483) |

`DrDoS_LDAP` — тоже UDP-атака (без единого TCP-флага в трафике), но её recall не просто выше, чем у `Syn`, а местами лучший из трёх (Isolation Forest — 0.500 против 0.304 на TCP). Значит `syn_ratio` — не главная причина провала на `UDPLag`: реальная переменная — насколько объёмна атака сама по себе. `Syn` и `DrDoS_LDAP` — это заливка (много пакетов/байт, экстремальные `unique_dst_ports` или `payload_bytes_total` в окне), их видно по оставшимся 7 признакам почти так же хорошо, как и по 9; `UDPLag` — это низкообъёмная атака на задержку соединения, которая не выделяется по объёму вообще, и именно поэтому она — а не «UDP vs TCP» — оказалась тем конкретным случаем, где урезанный набор признаков ловит атаку хуже всего.

**Ограничение честности.** Все три прогона — один датасет (CIC-DDoS2019, день `01-12`); FPR на `benign`-окнах чужой сети во всех трёх — 0.22–0.39, стабильно высокий независимо от типа атаки, что и является главным систематическим выводом M10, а не отличие между атаками. CIC-IDS2017 (другой год, датасет с не-DDoS сценариями вроде брутфорса и инфильтрации) и остальные файлы CIC-DDoS2019 пока не проверялись.

## Смещение между эмуляцией и настоящим инструментом (M11)

Разделы выше проверяют устойчивость к перемене интенсивности и переносу на чужую сеть. Третий вид дрейфа — более узкий, но внутри самого `dns_tunnel`: лаборатория размечает два сценария одной и той же меткой (`label = dns_tunnel`), но разным `scenario` — `dns_tunnel` (`lab/dns_tunnel.py`, эмуляция запросами по расписанию) и `iodine_tunnel` (настоящий `iodine` через контейнер `tunnel`, реальная передача данных через `dns0`). Раз оба попадают в одну выборку как один класс атаки, стоит явно проверить, не переобучается ли модель только на особенностях эмуляции, упуская то, чем настоящий туннель отличается на практике — то, на что README лаборатории раньше только намекал («для проверки на смещение стоит использовать оба»), без отдельного прогона и цифр.

**Прогон.** 4 запуска `dns_tunnel` (`rate=20`, `qtype=mixed`, `duration=20`) и 4 запуска `iodine_tunnel` (`duration=25`) в одной лабораторной сессии, та же выгрузка и то же разбиение (`--seed 0`), что и везде выше — `scenario` у обоих сценариев уже отдельная колонка в `labeled_flows`/`labeled_dns`, то есть `evaluate_baseline_by_scenario` (используется во всех `baseline_*_w5.json` в `baselines.md`) и без того считает recall по каждому из них отдельно; этот раздел — не новый код, а то, что эти два числа ещё никто не сравнил напрямую.

**Результат.** Recall на test-сплите (1 запуск каждого сценария — именно так распределяют 4 запуска сплит-пропорции 0.6/0.2/0.2, см. оговорку ниже):

| Baseline | `dns_tunnel` (эмуляция) | `iodine_tunnel` (настоящий) |
|---|---|---|
| threshold | recall 1.000 (precision 1.000) | recall 0.842 (precision 1.000) |
| Isolation Forest | recall 1.000 | recall 1.000 |
| Random Forest | recall 1.000 | recall 1.000 |
| Gradient Boosting | recall 1.000 | recall 1.000 |

Единственный заметный разрыв — у порогового baseline (0.842 против 1.000): остальные три модели, обученные сразу на обоих сценариях совместно (а не отдельно на каждом), ловят настоящий туннель так же хорошо, как эмуляцию — в этом датасете разница между эмуляцией и реальным инструментом не стала системной проблемой ни для одной модели с учителем или ансамблем, только для самого простого детектора.

**Почему порог всё-таки промахивается на части окон `iodine_tunnel`, а не на `dns_tunnel`.** Сравнение признаков между сценариями показывает, чем они реально отличаются: `dns_entropy_mean` у эмуляции выше (4.53 против 3.31 у `iodine`) — то есть по энтропии имён настоящий туннель выглядит даже спокойнее эмуляции, не тревожнее; зато `packets_total` на окно у `iodine` в среднем **3261** против **80** у эмуляции — настоящий туннель на порядки объёмнее, потому что реально передаёт данные через `dns0`, а не просто шлёт запросы по расписанию. Пороговый baseline не содержит правила по абсолютному объёму трафика для DNS-сценариев (`packets_total` в его списке признаков калибруется по общему, не DNS-специфичному квантилю) — и именно поэтому часть низкоактивных окон `iodine_tunnel` (вероятно, фаза установления сессии) проходит мимо, тогда как Random Forest/Gradient Boosting, обучаясь на полном наборе признаков сразу, подхватывают этот объёмный сигнал без явного правила под него.

**Ограничение честности.** 4 запуска на сценарий — это тест-сплит из одного запуска на сторону, то же ограничение малой выборки, что и выше: единственный плохой (или редкий) запуск `iodine_tunnel` неотличим от систематической слабости на таком размере, а recall 1.000 у трёх из четырёх baseline'ов на обоих сценариях может означать как «модель действительно не видит разницы», так и «эта конкретная лабораторная сессия оказалась слишком лёгкой для обоих сценариев». Настоящая проверка смещения требует кампании с несколькими независимыми сессиями (не только несколькими запусками подряд в одной), как и выше.

## Отслеживание экспериментов (MLflow)

Каждый запуск `baseline threshold`/`baseline isolation-forest`/`baseline random-forest`/`evaluate compare` дополнительно логируется в MLflow: параметры запуска (окно, `target_fpr`/`contamination`, подобранные гиперпараметры), метрики по каждому сплиту и сам JSON-отчёт как артефакт. По умолчанию — локально, без какой-либо инфраструктуры (файл/база в текущей директории), эксперимент называется `netstream-baselines`.

```bash
uv run netstream-ml baseline threshold data/v1 --window 5
uv run mlflow ui   # http://127.0.0.1:5000 — сравнение прогонов таблицей и графиками
```

Смысл — не заменить JSON-отчёты (они остаются источником правды для документации и скриптов), а дать быстрый способ визуально сравнить релизы модели друг с другом, не открывая файлы вручную: несколько прогонов `baseline random-forest` с разными сидами/гиперпараметрами сразу видны рядом в таблице MLflow UI с сортировкой по метрике.

Точка подключения — `MLFLOW_TRACKING_URI` (тот же принцип переопределения, что и у `CLICKHOUSE_URL`): если её нет, MLflow пишет в `./mlruns`/`mlflow.db` рядом с текущей директорией (в `.gitignore`, не коммитится); если она есть — данные идут на реальный MLflow-сервер (backend/deploy этот сервер пока не поднимают — это отдельная задача, если локальный вариант окажется полезным). Логирование никогда не роняет команду: если MLflow недоступен, в stderr печатается предупреждение, а сам отчёт всё равно считается и пишется как обычно.
