# Baseline-модели и фреймворк оценки

Нужен датасет и признаки — см. `datasets.md`.

## Baseline: пороговые правила

```bash
uv run netstream-ml baseline threshold data/v1 --window 5 --target-fpr 0.01
```

Для каждого признака из фиксированного списка (`aggregated_ratio`, `unique_dst_ports`, `packets_total`, `rst_ratio`, `syn_ratio`, `dns_txt_null_ratio`, `dns_entropy_mean`, `dns_unique_subdomains_max`) берётся квантиль `1 - target_fpr` его значений на доброкачественных строках **обучающей** выборки — порог, на котором этот признак сам по себе ложно сработал бы примерно на `target_fpr` доли benign-трафика. Правила объединяются через ИЛИ: сработало любое — окно помечено как атака. Никакого обучения, кроме чтения квантиля: это самый простой детектор, с которым нужно сравнивать любую модель, — если случайный лес не обгонит его с заметным запасом, лес не оправдывает сложность.

Команда требует, чтобы `features_w<N>.parquet` уже содержал колонку `split` (то есть `data split` был запущен до `features build`), считает метрики (precision, recall, F1, FPR, accuracy) на train/val/test и отдельно по каждому сценарию на test, пишет `baseline_threshold_w<N>.json`.

**Результат на реальном датасете** (92 запуска, окно 5 с): F1 = 0.66 на test, без переобучения (train/val/test близки — 0.663/0.667/0.661), что подтверждает: разбиение по `run_id` действительно не даёт утечки. По сценариям: `syn_flood`, `slow_scan`, `port_scan`, `dns_tunnel` (эмуляция) — recall 1.0, простые пороги их ловят полностью. `c2_beacon` (recall 0.33), `iodine_tunnel` (0.50), `slowloris` (0.29) — медленные и низкоскоростные атаки пороги почти не видят, это ожидаемо и ровно то, ради чего нужны модели (ниже). Ложные срабатывания сосредоточены на «трудных» доброкачественных профилях: `admin_scan` (FPR 1.0 — неотличим от `port_scan` по признакам потока, известное ограничение), `reputation_dns`, `backup`, `web_burst`, `cdn_dns` — то есть профили D3 действительно стресс-тестируют детектор, а не остаются недостижимым фоном.

## Baseline: Isolation Forest

```bash
uv run netstream-ml baseline isolation-forest data/v1 --window 5 --contamination 0.01
```

В отличие от порогового baseline, здесь одна модель обучается сразу на всём наборе признаков (`netstream_ml.features.FEATURE_COLUMNS`, признак, отсутствующий в кадре, просто пропускается) и учится не по правилу «одно значение вне диапазона», а по необычному **сочетанию** признаков — то, что пороги в принципе не видят: пороговое правило смотрит на каждый признак независимо, поэтому не заметит окно, где каждое отдельное значение само по себе не выходит за квантиль, но их совместное сочетание всё равно нетипично. Обучается только на доброкачественных строках **обучающей** выборки (`data split` перед `features build`, как и для порогов), атакующих примеров не требует. `--contamination` — доля обучающего доброкачественного трафика, которую модель сама пометит как выброс: играет ту же роль, что `--target-fpr` для порогов. DNS-признаки с `null` (окно без DNS-активности) заполняются нулём перед обучением — модель не умеет работать с пропусками, поэтому отсутствие DNS-активности неотличимо для неё от «нулевой» активности, хотя признаковый конвейер сам их различает.

Пишет `isolation_forest_w<N>.json` — тот же набор метрик и то же деление по сценариям, что и `baseline_threshold_w<N>.json`, для прямого сравнения.

**Результат на том же датасете.** При `--contamination 0.01` (столько же, сколько `target_fpr` у порогов): F1 = 0.48 на test — хуже порогового baseline (0.65), но за счёт совсем другого компромисса: recall ниже (0.36 против 0.67), зато `admin_scan` — единственный сценарий, где лес выигрывает принципиально: FPR падает с 1.0 (у порогов) до 0.0. Модель, глядя на весь набор признаков сразу, видит, что `admin_scan` в остальном ведёт себя иначе, чем настоящий `port_scan`, хотя по `unique_dst_ports` они неотличимы. Обратная сторона: `port_scan`, `slow_scan`, `syn_flood`, `slowloris` — сценарии, которые пороги ловили с recall 1.0 (первые три) или частично — при такой низкой контаминации лес пропускает полностью (recall 0.0): один аномальный признак растворяется среди двадцати трёх обычных.

При `--contamination 0.1` картина другая: F1 = 0.72 — уже лучше порогового baseline, recall 0.89 против 0.67. `c2_beacon` и `iodine_tunnel` — сценарии, которые пороги ловили лишь частично (0.33 и 0.50) — при этой настройке пойманы полностью (1.0). Но `admin_scan` возвращается к FPR 1.0 (как у порогов), и добавляются новые ложные срабатывания на части D3-профилей (`web_burst`, `udp_stream`, `video_stream`). `contamination` — это не константа, а рычаг конкретного компромисса precision/recall, и какая точка на этой кривой правильная, зависит от того, что дороже: пропущенная медленная атака или лишнее разбирательство по `admin_scan`.

Ни одна из двух настроек не побеждает пороговый baseline по всем осям сразу — это ожидаемый результат для одной модели без учителя на признаках, которые сами по себе уже неплохо разделяют большинство сценариев: там, где пороги работают, дополнительная сложность леса не окупается; там, где пороги проваливаются (медленные атаки, `admin_scan`), лес улучшает ситуацию, но не одновременно и то, и другое при одном значении `contamination`. Разница между `contamination=0.01` и `0.1` показывает, что этот параметр стоит подбирать по валидационной выборке под конкретную цель, а не оставлять по умолчанию.

**Поправка из «Фреймворка оценки» ниже**: сравнение через `evaluate compare` показывает, что разница F1 между порогами и Isolation Forest при `--contamination 0.01`, описанная выше, статистически не значима — эти два абзаца описывают реальные числа, но не стоит читать разницу F1 как «пороги увереннее лучше»: при размере теста лаборатории это могло с сопоставимой вероятностью получиться и в обратную сторону. Точные числа — в разделе «Фреймворк оценки» ниже.

## Baseline: Random Forest

```bash
uv run netstream-ml baseline random-forest data/v1 --window 5
```

В отличие от обеих предыдущих моделей, здесь используется размеченный **обучающий** трафик целиком, включая атаки, а не только доброкачественные окна: это уже не обнаружение аномалий, а прямая классификация «атака или нет» по всем доступным признакам сразу. Перед обучением команда сама подбирает гиперпараметры (`n_estimators` ∈ {100, 300}, `max_depth` ∈ {нет ограничения, 10, 20}, `class_weight` ∈ {нет, `balanced`} — фиксированная небольшая сетка, не вынесена в флаги CLI, чтобы не плодить конфигурацию, которую всё равно почти никогда не меняют вручную) по F1 на **валидационной** выборке, и только после этого модель с лучшими параметрами оценивается на train/val/test — сама сетка никогда не видит test, иначе тюнинг превратился бы в подгонку под контрольные данные. Финальная модель обучается на train (не train+val), чтобы оценки на val оставались честной проверкой, а не частью обучающих данных.

Пишет `random_forest_w<N>.json`: помимо тех же метрик, что и у двух других baseline'ов, там же лежит `tuning` — выбранные гиперпараметры, число перебранных комбинаций и F1 на val, на котором был сделан выбор.

**Результат на том же датасете.** Подобранная конфигурация (`n_estimators=300`, без ограничения глубины, без взвешивания классов) даёт F1 = 0.983 на test (precision 1.0, recall 0.967) — сильно выше и порогового baseline (0.65), и Isolation Forest в обеих настройках (0.48–0.72). Recall 1.0 без единого ложного срабатывания — на всех сценариях, включая ранее проблемные: `admin_scan` (FPR 0.0, как и лучшая настройка Isolation Forest), `c2_beacon`, `iodine_tunnel`, `slowloris` (recall 1.0 у всех трёх — пороги ловили их лишь частично, 0.33/0.50/0.29). Единственный не полностью пойманный сценарий — `udp_flood` (recall 0.67). Train F1 = 1.0 (дерево способно идеально разделить обучающую выборку целиком), но val (0.953) и test (0.983) не проседают — признак переобучения был бы разрыв между ними, а не сам по себе идеальный train.

Это ожидаемо: имея размеченные примеры атак, модель с учителем не обязана «спорить» — она напрямую учится на тех же атаках и профилях D3, на которых спотыкались пороги и IsolationForest. Именно поэтому этот результат нельзя читать как «лес — готовое решение»: он показывает верхнюю границу того, что вообще можно выжать из этого конкретного набора признаков и этого конкретного набора сценариев лаборатории, а не то, что модель обобщится на атаку, которой не было в обучающей выборке ни в каком виде. Ровно это и предстоит проверить в экспериментах переноса и смещения (`experiments.md`): высокий F1 здесь — не финальный ответ, а стартовая точка, которую ещё нужно подтвердить на данных, которые эта модель не видела даже отдалённо похожими.

## Baseline: Gradient Boosting (M7)

```bash
uv run netstream-ml baseline gradient-boosting data/v1 --window 5
```

Тот же принцип, что и у Random Forest (обучение на размеченных train-атаках, подбор гиперпараметров по F1 на val, оценка на train/val/test), но бустинг деревьев (`xgboost.XGBClassifier`) вместо их бэггинга — сетка поиска: `n_estimators` ∈ {100, 300}, `max_depth` ∈ {3, 6}, `learning_rate` ∈ {0.1, 0.3}. Смысл сравнения не в том, «кто лучше в целом» (на датасете в пару тысяч строк этот вопрос не имеет устойчивого ответа), а в том, согласны ли два разных алгоритма одного семейства на том, какие атаки трудные — согласие между ними честнее, чем скор одной-единственной модели. Пишет `gradient_boosting_w<N>.json` в том же формате, что и `random_forest_w<N>.json`.

**Полный прогон на всех сценариях лаборатории (как у Random Forest, 92+ запусков) пока не снят.** Частичный реальный прогон есть — `experiments.md`, раздел «Смещение между эмуляцией и настоящим инструментом (M11)» обучает и оценивает Gradient Boosting на `dns_tunnel`/`iodine_tunnel` (recall 1.000 на обоих в тест-сплите), так что модель на реальных данных уже проверена и работает. Но это только два сценария из полного набора `v1.yaml`: f1/precision/recall по всем классам атак разом (то, что есть у Random Forest в этом разделе) требует отдельного прогона полной кампании, который пока не делался. Код и тесты (включая `test_gradient_boosting.py`, построенный на тех же синтетических проверках, что и `test_supervised.py`) не зависят от реального прогона и проверены полностью.

## Фреймворк оценки (M8)

```bash
uv run netstream-ml evaluate compare data/v1 --window 5
```

Три инструмента, не привязанные к конкретной модели (`netstream_ml.evaluation`), решают одну проблему: у каждого baseline'а выше — одна точка (precision/recall/F1 при том пороге, `contamination` или гиперпараметрах, что заданы сейчас), а не то, насколько этой точке можно доверять.

- **PR-кривая** (`precision_recall_curve`) — весь компромисс precision/recall при любом возможном пороге решения, а не только та точка, где сейчас стоит `--target-fpr`, `--contamination` или выбор `random-forest`'а после тюнинга. Требует непрерывного скора, а не булева предсказания: `ThresholdBaseline.decision_score` — наибольшее нормализованное превышение порога среди всех правил, `IsolationForestBaseline.decision_score` — инвертированная `decision_function` (у sklearn выше = нормальнее, для PR-кривой нужно наоборот), `RandomForestBaseline.decision_score` — вероятность класса «атака». Итог — `average_precision`: площадь под кривой, одно число, но по всей кривой, а не по одной точке.
- **Разброс по seed** (`seed_sensitivity`) — модель с рандомизацией (Isolation Forest, случайный лес) переобучается на нескольких `random_state`, метрика (по умолчанию F1) считается на каждом прогоне; среднее, стандартное отклонение, минимум и максимум показывают, насколько результат — свойство данных, а не удачно выпавшего сида. Пороговый baseline здесь не участвует: в нём нет случайности, разброс по seed для него всегда будет нулевым.
- **Статзначимость** (`mcnemar_test`) — точный биномиальный тест Макнемара на тех строках, где два baseline'а разошлись: одна модель права, другая нет. Именно такие строки несут информацию о том, какая модель лучше; строки, где обе правы или обе ошиблись, отбрасываются как неинформативные. Даёт p-value — вероятность увидеть такое расхождение (или большее), если бы обе модели были одинаково хороши.

Команда `evaluate compare` сводит все три инструмента для всех четырёх baseline'ов разом (для случайного леса и градиентного бустинга используется та же сетка гиперпараметров, что и в `baseline random-forest`/`baseline gradient-boosting`, тюнинг на `val`) и пишет `evaluate_compare_w<N>.json`: PR-кривые и `average_precision` для каждой модели, разброс по seed для Isolation Forest, Random Forest и Gradient Boosting, шесть попарных тестов Макнемара (все сочетания из четырёх моделей).

**Результат на реальном датасете (три baseline'а, без Gradient Boosting).** `average_precision`: пороги 0.644, Isolation Forest 0.738, Random Forest 0.997 — лес с учителем ранжирует почти идеально, что согласуется с его F1 = 0.983 (раздел Random Forest выше). Разброс F1 по пяти сидам (0–4): у Isolation Forest среднее 0.434, отклонение 0.036 — заметный разброс, отдельный прогон может отличаться от среднего на несколько пунктов F1; у Random Forest среднее 0.983, отклонение **0.000** — на этом датасете результат воспроизводится от сида к сиду с точностью до третьего знака, то есть более ранний отчёт `baseline random-forest` (F1 = 0.983 на одном конкретном сиде) не был счастливой случайностью. McNemar: порог vs Isolation Forest — `p = 0.7359`, различие не значимо (см. поправку выше); порог vs Random Forest и Isolation Forest vs Random Forest — оба `p < 0.0001`, различие в пользу леса с учителем более чем убедительное. Итоговая картина: там, где сравниваются два примерно одинаково слабых детектора (пороги и Isolation Forest без разметки атак), McNemar предостерегает от поспешных выводов; там, где один детектор действительно намного лучше (Random Forest, обученный на разметке), тот же тест это подтверждает, а не опровергает — статзначимость работает в обе стороны, а не только «на понижение».

**Gradient Boosting в сравнении — код есть, цифры на полном датасете лаборатории пока не сняты.** Команда поддерживает четвёртую модель с момента, когда `baseline gradient-boosting` (M7) появился после того, как этот раздел и его результаты (три baseline'а выше) уже были написаны — сравнение кода проверено (`test_evaluate_compare_writes_a_report` гоняет все четыре модели и все шесть попарных McNemar на синтетических данных), но `average_precision`/разброс по сидам/McNemar для Gradient Boosting на тех же 92+ запусках лаборатории, что и у трёх остальных baseline выше, требуют нового прогона `evaluate compare` на полной кампании `v1.yaml` — она не была перезапущена ради этой правки. Частичная реальная проверка самой модели (без этого сравнительного фреймворка) уже есть — см. раздел «Полный прогон… пока не снят» у Gradient Boosting выше и `experiments.md`.
