# Baseline-модели и фреймворк оценки

Нужен датасет и признаки — см. `datasets.md`.

## Baseline: пороговые правила

```bash
uv run netstream-ml baseline threshold data/v1 --window 5 --target-fpr 0.01
```

Для каждого признака из фиксированного списка (`aggregated_ratio`, `unique_dst_ports`, `packets_total`, `rst_ratio`, `syn_ratio`, `dns_txt_null_ratio`, `dns_entropy_mean`, `dns_unique_subdomains_max`) берётся квантиль `1 - target_fpr` его значений на доброкачественных строках **обучающей** выборки — порог, на котором этот признак сам по себе ложно сработал бы примерно на `target_fpr` доли benign-трафика. Правила объединяются через ИЛИ: сработало любое — окно помечено как атака. Никакого обучения, кроме чтения квантиля: это самый простой детектор, с которым нужно сравнивать любую модель, — если случайный лес не обгонит его с заметным запасом, лес не оправдывает сложность.

Команда требует, чтобы `features_w<N>.parquet` уже содержал колонку `split` (то есть `data split` был запущен до `features build`), считает метрики (precision, recall, F1, FPR, accuracy) на train/val/test и отдельно по каждому сценарию на test, пишет `baseline_threshold_w<N>.json`.

**Результат на реальном датасете** (полная кампания `lab/campaigns/v1.yaml`, 46 запусков, окно 5 с — все четыре baseline ниже и «Фреймворк оценки» считаны на этом же, едином прогоне, одним и тем же `data/v1`): F1 = 0.81 на test (precision 0.929, recall 0.722, FPR 0.0055); train/val F1 ниже (0.569/0.613) — не переобучение, а то, что test-сплит в этой кампании оказался легче по составу сценариев (см. ниже), не то, что модель лучше работает на невиданных данных. По сценариям на test: `dns_tunnel`, `port_scan`, `syn_flood` — recall 1.0, простые пороги их ловят полностью; `udp_flood` — recall 0.0, пороги пропускают его целиком (ни один из восьми фиксированных признаков не выходит за квантиль на этом сценарии при такой интенсивности). Тестовый сплит этой кампании покрывает всего пять групп (`background`, `dns_tunnel`, `port_scan`, `syn_flood`, `udp_flood`) — заметно меньше, чем в более крупных прогонах, потому что большинство сценариев `v1.yaml` рассчитаны на 1–2 повтора и не всегда попадают в test при разбиении по `run_id` (см. `datasets.md`, «Разбиение на выборки» — это ограничение размера лабораторной кампании, не ошибка разбиения).

## Baseline: Isolation Forest

```bash
uv run netstream-ml baseline isolation-forest data/v1 --window 5 --contamination 0.01
```

В отличие от порогового baseline, здесь одна модель обучается сразу на всём наборе признаков (`netstream_ml.features.FEATURE_COLUMNS`, признак, отсутствующий в кадре, просто пропускается) и учится не по правилу «одно значение вне диапазона», а по необычному **сочетанию** признаков — то, что пороги в принципе не видят: пороговое правило смотрит на каждый признак независимо, поэтому не заметит окно, где каждое отдельное значение само по себе не выходит за квантиль, но их совместное сочетание всё равно нетипично. Обучается только на доброкачественных строках **обучающей** выборки (`data split` перед `features build`, как и для порогов), атакующих примеров не требует. `--contamination` — доля обучающего доброкачественного трафика, которую модель сама пометит как выброс: играет ту же роль, что `--target-fpr` для порогов. DNS-признаки с `null` (окно без DNS-активности) заполняются нулём перед обучением — модель не умеет работать с пропусками, поэтому отсутствие DNS-активности неотличимо для неё от «нулевой» активности, хотя признаковый конвейер сам их различает.

Пишет `isolation_forest_w<N>.json` — тот же набор метрик и то же деление по сценариям, что и `baseline_threshold_w<N>.json`, для прямого сравнения.

**Результат на том же датасете.** При `--contamination 0.01` (столько же, сколько `target_fpr` у порогов, и значение, которое использует `evaluate compare` ниже): F1 = 0.50 на test — хуже порогового baseline (0.81), с тем же, но более резким перекосом: recall 0.33 против 0.72 у порогов, зато precision 1.0 (ни одного ложного срабатывания вообще). По сценариям лес на этой настройке ловит только `dns_tunnel` (recall 1.0) — `port_scan`, `syn_flood`, `udp_flood` пропущены целиком (recall 0.0): при такой низкой контаминации модель помечает выбросом только самые редкие сочетания признаков, а три из четырёх тестовых атак недостаточно аномальны на фоне всего обучающего распределения признаков сразу.

При `--contamination 0.1` картина другая: F1 = 0.92 на test (precision 0.895, recall 0.944) — уже заметно лучше порогового baseline. `port_scan` и `syn_flood`, которые при `contamination=0.01` пропускались целиком, здесь пойманы полностью (recall 1.0); `udp_flood` — recall 0.8, лучше, чем 0.0 у порогов, но не идеально. `contamination` — это не константа, а рычаг конкретного компромисса precision/recall: выше контаминация — шире разброс того, что модель готова счесть «подозрительным», и ниже порог для срабатывания на реальной атаке, но и выше риск ложных срабатываний на редком, но безобидном трафике.

`contamination=0.01` не побеждает пороговый baseline ни по одной оси, кроме precision; `contamination=0.1` — побеждает по F1 целиком, в том числе именно на сценарии (`udp_flood`), который пороги пропускали полностью. Разница между `contamination=0.01` и `0.1` показывает, что этот параметр стоит подбирать по валидационной выборке под конкретную цель, а не оставлять по умолчанию.

**Поправка из «Фреймворка оценки» ниже**: сравнение через `evaluate compare` показывает, что разница F1 между порогами и Isolation Forest при `--contamination 0.01`, описанная выше, статистически не значима — эти два абзаца описывают реальные числа, но не стоит читать разницу F1 как «пороги увереннее лучше»: при размере теста лаборатории это могло с сопоставимой вероятностью получиться и в обратную сторону. Точные числа — в разделе «Фреймворк оценки» ниже.

## Baseline: Random Forest

```bash
uv run netstream-ml baseline random-forest data/v1 --window 5
```

В отличие от обеих предыдущих моделей, здесь используется размеченный **обучающий** трафик целиком, включая атаки, а не только доброкачественные окна: это уже не обнаружение аномалий, а прямая классификация «атака или нет» по всем доступным признакам сразу. Перед обучением команда сама подбирает гиперпараметры (`n_estimators` ∈ {100, 300}, `max_depth` ∈ {нет ограничения, 10, 20}, `class_weight` ∈ {нет, `balanced`} — фиксированная небольшая сетка, не вынесена в флаги CLI, чтобы не плодить конфигурацию, которую всё равно почти никогда не меняют вручную) по F1 на **валидационной** выборке, и только после этого модель с лучшими параметрами оценивается на train/val/test — сама сетка никогда не видит test, иначе тюнинг превратился бы в подгонку под контрольные данные. Финальная модель обучается на train (не train+val), чтобы оценки на val оставались честной проверкой, а не частью обучающих данных.

Пишет `random_forest_w<N>.json`: помимо тех же метрик, что и у двух других baseline'ов, там же лежит `tuning` — выбранные гиперпараметры, число перебранных комбинаций и F1 на val, на котором был сделан выбор.

**Результат на том же датасете.** Подобранная конфигурация (`n_estimators=100`, `max_depth=10`, без взвешивания классов, выбрана по F1=0.894 на val из 12 перебранных комбинаций) даёт F1 = 0.703 на test (precision 0.684, recall 0.722) — между пороговым baseline (0.81) и лучшей настройкой Isolation Forest (0.92), не выше обоих: train F1 = 0.992, val F1 = 0.894, test F1 = 0.703 — падение от train к test заметно больше, чем у порогов или Isolation Forest, похоже на переобучение на небольшой обучающей выборке (475 строк train), а не на полное обобщение. По сценариям: `dns_tunnel`, `port_scan` — recall 1.0; `syn_flood` — recall 0.833 (f1 0.909); `udp_flood` — recall лишь 0.2 (f1 0.333) — заметно хуже, чем у Isolation Forest при `contamination=0.1` (0.8) на этом же сценарии.

На этом конкретном прогоне (46 запусков, 475 строк train) модель с учителем не обгоняет baseline без разметки — не потому, что размеченное обучение в принципе не помогает, а потому, что обучающей выборки здесь мало относительно числа признаков и гиперпараметров, которые тюнинг перебирает по val: дерево успевает подогнаться под шум обучающей выборки раньше, чем находит устойчивый сигнал, который перенёсся бы на test. Сравнение с Gradient Boosting ниже (тот же принцип, другой алгоритм бустинга вместо бэггинга) показывает, что это ограничение — свойство модели и размера выборки, а не самого признакового пространства: на тех же признаках и том же разбиении градиентный бустинг обобщается заметно лучше, в частности именно на `udp_flood`, где случайный лес проседает больше всего.

## Baseline: Gradient Boosting (M7)

```bash
uv run netstream-ml baseline gradient-boosting data/v1 --window 5
```

Тот же принцип, что и у Random Forest (обучение на размеченных train-атаках, подбор гиперпараметров по F1 на val, оценка на train/val/test), но бустинг деревьев (`xgboost.XGBClassifier`) вместо их бэггинга — сетка поиска: `n_estimators` ∈ {100, 300}, `max_depth` ∈ {3, 6}, `learning_rate` ∈ {0.1, 0.3}. Смысл сравнения не в том, «кто лучше в целом» (на датасете в пару тысяч строк этот вопрос не имеет устойчивого ответа), а в том, согласны ли два разных алгоритма одного семейства на том, какие атаки трудные — согласие между ними честнее, чем скор одной-единственной модели. Пишет `gradient_boosting_w<N>.json` в том же формате, что и `random_forest_w<N>.json`.

**Результат на том же датасете, что и у Random Forest** (полная кампания `v1.yaml`, 46 запусков). Подобранная конфигурация (`n_estimators=100`, `max_depth=3`, `learning_rate=0.1`, выбрана по F1=0.902 на val из 8 перебранных комбинаций) даёт F1 = 0.872 на test (precision 0.810, recall 0.944) — заметно выше Random Forest (0.703) на этом же датасете и разбиении, и выше порогового baseline (0.81). По сценариям: `dns_tunnel`, `port_scan` — recall 1.0 (как у всех моделей); `syn_flood` — recall 0.833 (f1 0.909, идентично Random Forest); `udp_flood` — recall 1.0 (f1 1.0) — именно тот сценарий, на котором Random Forest проседал сильнее всего (recall 0.2). Train F1 = 0.977, val F1 = 0.902, test F1 = 0.872 — разрыв между выборками заметно меньше, чем у Random Forest, несмотря на более глубокую (бустинг) модель: меньшая глубина деревьев (`max_depth=3` против `max_depth=10` у выбранного Random Forest) и собственная регуляризация бустинга через `learning_rate`, судя по всему, здесь важнее для обобщения на маленькой выборке, чем число деревьев.

Частичный реальный прогон на данных другой, более ранней кампании (`dns_tunnel`/`iodine_tunnel`, recall 1.000 на обоих) есть также в `experiments.md`, раздел «Смещение между эмуляцией и настоящим инструментом (M11)» — согласуется с полным прогоном выше по направлению (`dns_tunnel` ловится полностью), но не по размеру выборки.

## Фреймворк оценки (M8)

```bash
uv run netstream-ml evaluate compare data/v1 --window 5
```

Три инструмента, не привязанные к конкретной модели (`netstream_ml.evaluation`), решают одну проблему: у каждого baseline'а выше — одна точка (precision/recall/F1 при том пороге, `contamination` или гиперпараметрах, что заданы сейчас), а не то, насколько этой точке можно доверять.

- **PR-кривая** (`precision_recall_curve`) — весь компромисс precision/recall при любом возможном пороге решения, а не только та точка, где сейчас стоит `--target-fpr`, `--contamination` или выбор `random-forest`'а после тюнинга. Требует непрерывного скора, а не булева предсказания: `ThresholdBaseline.decision_score` — наибольшее нормализованное превышение порога среди всех правил, `IsolationForestBaseline.decision_score` — инвертированная `decision_function` (у sklearn выше = нормальнее, для PR-кривой нужно наоборот), `RandomForestBaseline.decision_score` — вероятность класса «атака». Итог — `average_precision`: площадь под кривой, одно число, но по всей кривой, а не по одной точке.
- **Разброс по seed** (`seed_sensitivity`) — модель с рандомизацией (Isolation Forest, случайный лес) переобучается на нескольких `random_state`, метрика (по умолчанию F1) считается на каждом прогоне; среднее, стандартное отклонение, минимум и максимум показывают, насколько результат — свойство данных, а не удачно выпавшего сида. Пороговый baseline здесь не участвует: в нём нет случайности, разброс по seed для него всегда будет нулевым.
- **Статзначимость** (`mcnemar_test`) — точный биномиальный тест Макнемара на тех строках, где два baseline'а разошлись: одна модель права, другая нет. Именно такие строки несут информацию о том, какая модель лучше; строки, где обе правы или обе ошиблись, отбрасываются как неинформативные. Даёт p-value — вероятность увидеть такое расхождение (или большее), если бы обе модели были одинаково хороши.

Команда `evaluate compare` сводит все три инструмента для всех четырёх baseline'ов разом (для случайного леса и градиентного бустинга используется та же сетка гиперпараметров, что и в `baseline random-forest`/`baseline gradient-boosting`, тюнинг на `val`) и пишет `evaluate_compare_w<N>.json`: PR-кривые и `average_precision` для каждой модели, разброс по seed для Isolation Forest, Random Forest и Gradient Boosting, шесть попарных тестов Макнемара (все сочетания из четырёх моделей).

**Результат на реальном датасете (все четыре baseline'а, одна и та же кампания `v1.yaml`, 46 запусков, `--contamination` для Isolation Forest — значение по умолчанию 0.01, как в разделе Isolation Forest выше).** `average_precision`: пороги 0.747, Isolation Forest 0.931, Random Forest 0.871, Gradient Boosting 0.931 — Isolation Forest и Gradient Boosting ранжируют почти одинаково хорошо по всей PR-кривой целиком, несмотря на то, что их F1 в одной конкретной точке решения (раздел выше) сильно отличается (0.50 против 0.872): `average_precision` смотрит на весь диапазон порогов, а не только на тот, который сейчас выбран по умолчанию, — это ровно тот случай, ради которого PR-кривая, а не одна точка.

Разброс F1 по пяти сидам (0–4): у Isolation Forest среднее 0.500, отклонение 0.000 (с этой моделью/контаминацией результат детерминирован на этом датасете — сам алгоритм рандомизирован, но на этой выборке каждый сид сходится к одному и тому же разбиению); у Random Forest среднее 0.723, отклонение 0.017; у Gradient Boosting среднее 0.872, отклонение **0.000** — как и у Random Forest в более ранних (крупных) прогонах, результат воспроизводится от сида к сиду точно, то есть F1 = 0.872 из раздела Gradient Boosting выше не был счастливой случайностью одного конкретного `random_state`.

McNemar (все шесть пар): порог vs Isolation Forest — `p = 0.070`; порог vs Random Forest — `p = 0.180`; порог vs Gradient Boosting — `p = 1.000`; Isolation Forest vs Random Forest — `p = 1.000`; Isolation Forest vs Gradient Boosting — `p = 0.118`; **Random Forest vs Gradient Boosting — `p = 0.031`**, значимо на уровне 0.05, и односторонне: из строк, где они расходятся, Gradient Boosting оказывается прав 6 раз из 6, Random Forest — 0. На этом конкретном датасете это единственная пара с убедительной статистической разницей — ни пороги, ни Isolation Forest не расходятся с остальными моделями настолько систематически, чтобы McNemar это подтвердил при таком размере test-выборки (200 строк). Это согласуется с разделом Gradient Boosting выше: расхождение между Random Forest и Gradient Boosting сосредоточено в основном на `udp_flood` (recall 0.2 против 1.0) — не шум, а систематическая разница в том, какую атаку какая модель обобщает лучше.
