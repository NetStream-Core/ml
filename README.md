# NetStream ML

Датасеты, признаки, модели и оценка для детектора сетевых атак NetStream. Данные берутся из ClickHouse стека `deploy` (размеченные представления `labeled_flows` и `labeled_dns`), обученные модели используются онлайн-детектором.

## Состав

| Путь | Назначение |
|---|---|
| `src/netstream_ml/` | пакет и CLI `netstream-ml` |
| `tests/` | тесты |
| `data/` | выгрузки датасетов (не в git) |
| `artifacts/` | модели и отчёты (не в git) |

## Разработка

Нужны Python 3.12+ и [`uv`](https://docs.astral.sh/uv/).

```bash
uv sync
uv run pytest
just all
```

- `just format` форматирует и правит `ruff`.
- `just lint` запускает `ruff`, проверку форматирования и `mypy --strict`.
- `just test` запускает `pytest`.

## Выгрузка датасета

Нужен запущенный стек `deploy` (`just up` или лаборатория `just lab-up`/`just lab-campaign`) с доступным HTTP-интерфейсом ClickHouse.

```bash
uv run netstream-ml data export data/v1 \
    --url http://127.0.0.1:8123 \
    --campaign-manifest ../deploy/lab/campaigns/manifests/v1-<timestamp>.json
```

Подключение можно задать переменными окружения `CLICKHOUSE_URL`, `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD`, `CLICKHOUSE_DATABASE` вместо флагов.

`labeled_flows` и `labeled_dns` — представления, которые для каждой строки перебирают все окна из `labels`, поэтому на датасете с полсотней запусков и сотней тысяч потоков запрос может упереться в лимит памяти ClickHouse по умолчанию. `data export` сам поднимает `max_memory_usage` до 2 ГиБ (`--max-memory-usage` или `CLICKHOUSE_MAX_MEMORY_USAGE`); если и этого не хватает, поднимать дальше или выносить разметку в материализованную таблицу — отдельная задача для `deploy`.

Команда выгружает `labeled_flows`, `labeled_dns` и `labels` в `flows.parquet`, `dns.parquet` и `labels.parquet` (ClickHouse отдаёт Parquet сам через `FORMAT Parquet`, без промежуточной конвертации) и пишет `manifest.json`: версия `netstream-ml`, версия сервера ClickHouse, список сценариев, число строк и sha256 каждого файла. С `--campaign-manifest` в манифест выгрузки попадает содержимое манифеста кампании (`deploy/lab/campaign.py`) целиком, с его собственной контрольной суммой — так выгрузка прослеживается до конкретного прогона лаборатории, включая git-ревизию агента.

## Разбиение на выборки

```bash
uv run netstream-ml data split data/v1 --seed 0 --train 0.6 --val 0.2 --test 0.2
```

Команда читает `labels.parquet`, `flows.parquet` и `dns.parquet` из указанной директории (результат `data export`), добавляет колонку `split` (`train`/`val`/`test`) в `flows.parquet` и `dns.parquet` и пишет `split_manifest.json`.

Единица разбиения — запуск сценария (`run_id`), а не отдельная запись: все записи одного запуска атаки или доброкачественного профиля целиком уходят в одну выборку, чтобы модель не видела один и тот же инцидент и при обучении, и при проверке. Сценарий с тремя и более запусками представлен во всех трёх выборках (наибольший остаток, детерминированный порядок по seed); сценарий с одним-двумя запусками может не попасть в тест или в валидацию — это ограничение малой лаборатории, а не ошибка.

У фонового трафика (`scenario = background`, нет `run_id`) нет привязки к запуску — он идёт постоянно между сценариями. Такие записи группируются по 30-секундным интервалам времени, и каждый интервал целиком уходит в одну выборку. Это уменьшает, но не убирает утечку: фоновый поток, чей интервал съёма пересекает границу 30-секундного окна, может отдать часть своих записей в разные выборки.

Разбиение детерминировано (`--seed`): одинаковый seed на одном датасете даёт одинаковое разбиение, что нужно для воспроизводимости экспериментов. `split_manifest.json` фиксирует seed, доли выборок, разбиение по `run_id` и отчёт о проверке утечек (`check_run_leakage`) для `flows` и `dns`; команда возвращает код выхода `1`, если хоть один `run_id` оказался больше чем в одной выборке.

**Важно про порядок команд**: `features build` наследует колонку `split` из `flows.parquet`/`dns.parquet`, если она уже там есть (тем же правилом «последняя запись в окне», что и для `label`/`scenario`). Разбивать нужно **до** построения признаков — тогда у каждой строки признаков будет своя выборка и повторно считать признаки на train/val/test отдельно не придётся. Если `data split` не запускали, `features build` просто не добавит колонку `split`.

`run_id` переносится тем же правилом всегда, независимо от `data split` (он приходит из `labeled_flows`/`labeled_dns` сразу при экспорте) — по нему окно признаков можно привязать обратно к конкретному прогону лаборатории и его параметрам (`labels.params`), см. раздел «Чувствительность к интенсивности атаки» ниже.

## Признаки

```bash
uv run netstream-ml features build data/v1 --window 1 --window 5 --window 10
```

Читает `flows.parquet` и `dns.parquet` из директории выгрузки, считает признаки за скользящее по эпохе окно (по умолчанию 1, 5 и 10 секунд, флаг можно повторять) отдельно для каждого источника (`src_ip`) и пишет `features_w<N>.parquet` плюс `features_manifest.json` с числом строк по каждому окну.

Единица агрегации — источник за окно, а не отдельный поток: одна строка описывает, чем в данный момент занят конкретный хост (объём трафика, доля SYN/SYN-ACK/RST, доля пакетов, попавших в агрегированные записи агента при флуде, распределение по размеру пакетов, статистика межпакетных интервалов, число уникальных адресов и портов назначения; со стороны DNS — число запросов, длина и энтропия имён, доля TXT/NULL, доля запросов по TCP, максимум уникальных поддоменов). Метка и сценарий окна берутся из последней по времени записи в нём.

Расчёт живёт в `netstream_ml.features` как две реализации одной спецификации: `build_features` — быстрый батч на polars для обучения моделей, `WindowAccumulator` — простой инкрементальный накопитель для будущего онлайн-детектора (M16), который можно кормить записями по одной по мере поступления из Kafka. `tests/test_features_parity.py` прогоняет одни и те же сгенерированные данные через обе реализации и сверяет результат с точностью до `1e-9` — иначе легко незаметно разойтись и получить skew между обучением и продакшеном.

**Ограничения.** Окно короче, чем интервал съёма агента (`REPORT_INTERVAL_MS`, по умолчанию 1 с), не даст дополнительной гранулярности — запись потока уже агрегирована на уровне агента. Источник без DNS-активности в окне получает нулевые счётчики и `null` в средних/максимумах (там нечего усреднять). В лаборатории атакующий и обычный клиент — разные адреса, поэтому смешение меток внутри одного окна возможно только на границе запуска сценария. `synack_ratio` считается внутри окна одного источника и показывает долю его собственных SYN-пакетов, которые сами являются SYN-ACK (то есть источник отвечает на чужие подключения, а не проверку «дошли ли ответы на мои SYN»): ответ на SYN приходит от другого адреса и попадает в окно этого другого адреса, поэтому у атакующего источника `synack_ratio` почти всегда 0 — это ожидаемо, не признак того, что флуд не долетел до жертвы.

Проверено на реальном датасете (92 запуска лаборатории, 254 080 потоков, 105 812 DNS-записей после экспорта): `aggregated_ratio` у `syn_flood` в среднем 0.69 против 0.01 у `benign` (бюджет новых потоков агента исчерпывается именно на флуде, как и задумано), `dns_entropy_mean` у `dns_tunnel` — 3.96 против 3.19 у фонового трафика.

## Baseline: пороговые правила

```bash
uv run netstream-ml baseline threshold data/v1 --window 5 --target-fpr 0.01
```

Для каждого признака из фиксированного списка (`aggregated_ratio`, `unique_dst_ports`, `packets_total`, `rst_ratio`, `syn_ratio`, `dns_txt_null_ratio`, `dns_entropy_mean`, `dns_unique_subdomains_max`) берётся квантиль `1 - target_fpr` его значений на доброкачественных строках **обучающей** выборки — порог, на котором этот признак сам по себе ложно сработал бы примерно на `target_fpr` доли benign-трафика. Правила объединяются через ИЛИ: сработало любое — окно помечено как атака. Никакого обучения, кроме чтения квантиля: это самый простой детектор, с которым нужно сравнивать любую модель, — если случайный лес не обгонит его с заметным запасом, лес не оправдывает сложность.

Команда требует, чтобы `features_w<N>.parquet` уже содержал колонку `split` (то есть `data split` был запущен до `features build`), считает метрики (precision, recall, F1, FPR, accuracy) на train/val/test и отдельно по каждому сценарию на test, пишет `baseline_threshold_w<N>.json`.

**Результат на реальном датасете** (92 запуска, окно 5 с): F1 = 0.66 на test, без переобучения (train/val/test близки — 0.663/0.667/0.661), что подтверждает: разбиение по `run_id` действительно не даёт утечки. По сценариям: `syn_flood`, `slow_scan`, `port_scan`, `dns_tunnel` (эмуляция) — recall 1.0, простые пороги их ловят полностью. `c2_beacon` (recall 0.33), `iodine_tunnel` (0.50), `slowloris` (0.29) — медленные и низкоскоростные атаки пороги почти не видят, это ожидаемо и ровно то, ради чего нужны модели (M6–M7). Ложные срабатывания сосредоточены на «трудных» доброкачественных профилях: `admin_scan` (FPR 1.0 — неотличим от `port_scan` по признакам потока, известное ограничение), `reputation_dns`, `backup`, `web_burst`, `cdn_dns` — то есть профили D3 действительно стресс-тестируют детектор, а не остаются недостижимым фоном.

## Baseline: Isolation Forest

```bash
uv run netstream-ml baseline isolation-forest data/v1 --window 5 --contamination 0.01
```

В отличие от порогового baseline, здесь одна модель обучается сразу на всём наборе признаков (`netstream_ml.features.FEATURE_COLUMNS`, признак, отсутствующий в кадре, просто пропускается) и учится не по правилу «одно значение вне диапазона», а по необычному **сочетанию** признаков — то, что пороги в принципе не видят: пороговое правило смотрит на каждый признак независимо, поэтому не заметит окно, где каждое отдельное значение само по себе не выходит за квантиль, но их совместное сочетание всё равно нетипично. Обучается только на доброкачественных строках **обучающей** выборки (`data split` перед `features build`, как и для порогов), атакующих примеров не требует. `--contamination` — доля обучающего доброкачественного трафика, которую модель сама пометит как выброс: играет ту же роль, что `--target-fpr` для порогов. DNS-признаки с `null` (окно без DNS-активности) заполняются нулём перед обучением — модель не умеет работать с пропусками, поэтому отсутствие DNS-активности неотличимо для неё от «нулевой» активности, хотя признаковый конвейер сам их различает.

Пишет `isolation_forest_w<N>.json` — тот же набор метрик и то же деление по сценариям, что и `baseline_threshold_w<N>.json`, для прямого сравнения.

**Результат на том же датасете.** При `--contamination 0.01` (столько же, сколько `target_fpr` у порогов): F1 = 0.48 на test — хуже порогового baseline (0.65), но за счёт совсем другого компромисса: recall ниже (0.36 против 0.67), зато `admin_scan` — единственный сценарий, где лес выигрывает принципиально: FPR падает с 1.0 (у порогов) до 0.0. Модель, глядя на весь набор признаков сразу, видит, что `admin_scan` в остальном ведёт себя иначе, чем настоящий `port_scan`, хотя по `unique_dst_ports` они неотличимы. Обратная сторона: `port_scan`, `slow_scan`, `syn_flood`, `slowloris` — сценарии, которые пороги ловили с recall 1.0 (первые три) или частично — при такой низкой контаминации лес пропускает полностью (recall 0.0): один аномальный признак растворяется среди двадцати трёх обычных.

При `--contamination 0.1` картина другая: F1 = 0.72 — уже лучше порогового baseline, recall 0.89 против 0.67. `c2_beacon` и `iodine_tunnel` — сценарии, которые пороги ловили лишь частично (0.33 и 0.50) — при этой настройке пойманы полностью (1.0). Но `admin_scan` возвращается к FPR 1.0 (как у порогов), и добавляются новые ложные срабатывания на части D3-профилей (`web_burst`, `udp_stream`, `video_stream`). `contamination` — это не константа, а рычаг конкретного компромисса precision/recall, и какая точка на этой кривой правильная, зависит от того, что дороже: пропущенная медленная атака или лишнее разбирательство по `admin_scan`.

Ни одна из двух настроек не побеждает пороговый baseline по всем осям сразу — это ожидаемый результат для одной модели без учителя на признаках, которые сами по себе уже неплохо разделяют большинство сценариев: там, где пороги работают, дополнительная сложность леса не окупается; там, где пороги проваливаются (медленные атаки, `admin_scan`), лес улучшает ситуацию, но не одновременно и то, и другое при одном значении `contamination`. Разница между `contamination=0.01` и `0.1` показывает, что этот параметр стоит подбирать по валидационной выборке под конкретную цель, а не оставлять по умолчанию.

**Поправка из M8**: сравнение через `evaluate compare` (ниже) показывает, что разница F1 между порогами и Isolation Forest при `--contamination 0.01`, описанная выше, статистически не значима — эти два абзаца описывают реальные числа, но не стоит читать разницу F1 как «пороги увереннее лучше»: при размере теста лаборатории это могло с сопоставимой вероятностью получиться и в обратную сторону. Точные числа — в разделе M8.

## Baseline: Random Forest

```bash
uv run netstream-ml baseline random-forest data/v1 --window 5
```

В отличие от обеих предыдущих моделей, здесь используется размеченный **обучающий** трафик целиком, включая атаки, а не только доброкачественные окна: это уже не обнаружение аномалий, а прямая классификация «атака или нет» по всем доступным признакам сразу. Перед обучением команда сама подбирает гиперпараметры (`n_estimators` ∈ {100, 300}, `max_depth` ∈ {нет ограничения, 10, 20}, `class_weight` ∈ {нет, `balanced`} — фиксированная небольшая сетка, не вынесена в флаги CLI, чтобы не плодить конфигурацию, которую всё равно почти никогда не меняют вручную) по F1 на **валидационной** выборке, и только после этого модель с лучшими параметрами оценивается на train/val/test — сама сетка никогда не видит test, иначе тюнинг превратился бы в подгонку под контрольные данные. Финальная модель обучается на train (не train+val), чтобы оценки на val оставались честной проверкой, а не частью обучающих данных.

Пишет `random_forest_w<N>.json`: помимо тех же метрик, что и у двух других baseline'ов, там же лежит `tuning` — выбранные гиперпараметры, число перебранных комбинаций и F1 на val, на котором был сделан выбор.

**Результат на том же датасете.** Подобранная конфигурация (`n_estimators=300`, без ограничения глубины, без взвешивания классов) даёт F1 = 0.983 на test (precision 1.0, recall 0.967) — сильно выше и порогового baseline (0.65), и Isolation Forest в обеих настройках (0.48–0.72). Recall 1.0 без единого ложного срабатывания — на всех сценариях, включая ранее проблемные: `admin_scan` (FPR 0.0, как и лучшая настройка Isolation Forest), `c2_beacon`, `iodine_tunnel`, `slowloris` (recall 1.0 у всех трёх — пороги ловили их лишь частично, 0.33/0.50/0.29). Единственный не полностью пойманный сценарий — `udp_flood` (recall 0.67). Train F1 = 1.0 (дерево способно идеально разделить обучающую выборку целиком), но val (0.953) и test (0.983) не проседают — признак переобучения был бы разрыв между ними, а не сам по себе идеальный train.

Это ожидаемо: имея размеченные примеры атак, модель с учителем не обязана «спорить» — она напрямую учится на тех же атаках и профилях D3, на которых спотыкались пороги и IsolationForest. Именно поэтому этот результат нельзя читать как «лес — готовое решение»: он показывает верхнюю границу того, что вообще можно выжать из этого конкретного набора признаков и этого конкретного набора сценариев лаборатории, а не то, что модель обобщится на атаку, которой не было в обучающей выборке ни в каком виде. Ровно это и предстоит проверить в M10 (перенос на CIC-IDS2017/CIC-DDoS2019) и M11 (эксперимент с дрейфом): высокий F1 здесь — не финальный ответ, а стартовая точка, которую ещё нужно подтвердить на данных, которые эта модель не видела даже отдалённо похожими.

## Baseline: Gradient Boosting (M7)

```bash
uv run netstream-ml baseline gradient-boosting data/v1 --window 5
```

Тот же принцип, что и у Random Forest (обучение на размеченных train-атаках, подбор гиперпараметров по F1 на val, оценка на train/val/test), но бустинг деревьев (`xgboost.XGBClassifier`) вместо их бэггинга — сетка поиска: `n_estimators` ∈ {100, 300}, `max_depth` ∈ {3, 6}, `learning_rate` ∈ {0.1, 0.3}. Смысл сравнения не в том, «кто лучше в целом» (на датасете в пару тысяч строк этот вопрос не имеет устойчивого ответа), а в том, согласны ли два разных алгоритма одного семейства на том, какие атаки трудные — согласие между ними честнее, чем скор одной-единственной модели. Пишет `gradient_boosting_w<N>.json` в том же формате, что и `random_forest_w<N>.json`.

**Полный прогон на всех сценариях лаборатории (как у Random Forest, 92+ запусков) пока не снят.** Частичный реальный прогон есть — раздел «Смещение между эмуляцией и настоящим инструментом (M11)» ниже обучает и оценивает Gradient Boosting на `dns_tunnel`/`iodine_tunnel` (recall 1.000 на обоих в тест-сплите), так что модель на реальных данных уже проверена и работает. Но это только два сценария из полного набора `v1.yaml`: f1/precision/recall по всем классам атак разом (то, что есть у Random Forest в этом разделе) требует отдельного прогона полной кампании, который пока не делался. Код и тесты (включая `test_gradient_boosting.py`, построенный на тех же синтетических проверках, что и `test_supervised.py`) не зависят от реального прогона и проверены полностью.

## Фреймворк оценки (M8)

```bash
uv run netstream-ml evaluate compare data/v1 --window 5
```

Три инструмента, не привязанные к конкретной модели (`netstream_ml.evaluation`), решают одну проблему: у каждого baseline'а выше — одна точка (precision/recall/F1 при том пороге, `contamination` или гиперпараметрах, что заданы сейчас), а не то, насколько этой точке можно доверять.

- **PR-кривая** (`precision_recall_curve`) — весь компромисс precision/recall при любом возможном пороге решения, а не только та точка, где сейчас стоит `--target-fpr`, `--contamination` или выбор `random-forest`'а после тюнинга. Требует непрерывного скора, а не булева предсказания: `ThresholdBaseline.decision_score` — наибольшее нормализованное превышение порога среди всех правил, `IsolationForestBaseline.decision_score` — инвертированная `decision_function` (у sklearn выше = нормальнее, для PR-кривой нужно наоборот), `RandomForestBaseline.decision_score` — вероятность класса «атака». Итог — `average_precision`: площадь под кривой, одно число, но по всей кривой, а не по одной точке.
- **Разброс по seed** (`seed_sensitivity`) — модель с рандомизацией (Isolation Forest, случайный лес) переобучается на нескольких `random_state`, метрика (по умолчанию F1) считается на каждом прогоне; среднее, стандартное отклонение, минимум и максимум показывают, насколько результат — свойство данных, а не удачно выпавшего сида. Пороговый baseline здесь не участвует: в нём нет случайности, разброс по seed для него всегда будет нулевым.
- **Статзначимость** (`mcnemar_test`) — точный биномиальный тест Макнемара на тех строках, где два baseline'а разошлись: одна модель права, другая нет. Именно такие строки несут информацию о том, какая модель лучше; строки, где обе правы или обе ошиблись, отбрасываются как неинформативные. Даёт p-value — вероятность увидеть такое расхождение (или большее), если бы обе модели были одинаково хороши.

Команда `evaluate compare` сводит все три инструмента для всех четырёх baseline'ов разом (для случайного леса и градиентного бустинга используется та же сетка гиперпараметров, что и в `baseline random-forest`/`baseline gradient-boosting`, тюнинг на `val`) и пишет `evaluate_compare_w<N>.json`: PR-кривые и `average_precision` для каждой модели, разброс по seed для Isolation Forest, Random Forest и Gradient Boosting, шесть попарных тестов Макнемара (все сочетания из четырёх моделей).

**Результат на реальном датасете (три baseline'а, без Gradient Boosting).** `average_precision`: пороги 0.644, Isolation Forest 0.738, Random Forest 0.997 — лес с учителем ранжирует почти идеально, что согласуется с его F1 = 0.983 (раздел выше). Разброс F1 по пяти сидам (0–4): у Isolation Forest среднее 0.434, отклонение 0.036 — заметный разброс, отдельный прогон может отличаться от среднего на несколько пунктов F1; у Random Forest среднее 0.983, отклонение **0.000** — на этом датасете результат воспроизводится от сида к сиду с точностью до третьего знака, то есть более ранний отчёт `baseline random-forest` (F1 = 0.983 на одном конкретном сиде) не был счастливой случайностью. McNemar: порог vs Isolation Forest — `p = 0.7359`, различие не значимо (см. поправку выше); порог vs Random Forest и Isolation Forest vs Random Forest — оба `p < 0.0001`, различие в пользу леса с учителем более чем убедительное. Итоговая картина: там, где сравниваются два примерно одинаково слабых детектора (пороги и Isolation Forest без разметки атак), McNemar предостерегает от поспешных выводов; там, где один детектор действительно намного лучше (Random Forest, обученный на разметке), тот же тест это подтверждает, а не опровергает — статзначимость работает в обе стороны, а не только «на понижение».

**Gradient Boosting в сравнении — код есть, цифры на полном датасете лаборатории пока не сняты.** Команда поддерживает четвёртую модель с момента, когда `baseline gradient-boosting` (M7) появился после того, как этот раздел и его результаты (три baseline'а выше) уже были написаны — сравнение кода проверено (`test_evaluate_compare_writes_a_report` гоняет все четыре модели и все шесть попарных McNemar на синтетических данных), но `average_precision`/разброс по сидам/McNemar для Gradient Boosting на тех же 92+ запусках лаборатории, что и у трёх остальных baseline выше, требуют нового прогона `evaluate compare` на полной кампании `v1.yaml` — она не была перезапущена ради этой правки. Частичная реальная проверка самой модели (без этого сравнительного фреймворка) уже есть — см. раздел «Полный прогон… пока не снят» у Gradient Boosting выше и M11 ниже.

## Чувствительность к интенсивности атаки (M9)

```bash
uv run netstream-ml evaluate intensity data/v1 --window 5
```

Все три baseline'а выше оцениваются на «типичном» прогоне каждого сценария — но `lab/run.sh` даёт каждому flood/scan/tunnel-сценарию параметр `--rate`, и кампания `v1.yaml` уже гоняет несколько сценариев на разных `rate` (`syn_flood` на 200/1000/5000 pps, `port_scan` на 50/500/1000 pps/с, `dns_tunnel` на 10/20/40 запросов/с, и т. д.) — то есть в уже накопленных данных лаборатории есть реальная вариация интенсивности, просто раньше не было способа привязать окно признаков обратно к параметрам породившего его запуска. Для этого `features build` теперь прокидывает `run_id` через агрегацию (тем же правилом «последняя запись в окне», что и для `label`/`scenario`/`split`), а `netstream_ml.intensity` соединяет его с `rate` из `labels.params`.

Модели обучаются как обычно на `train`; recall считается по `rate`-группам на **отложенных** строках (`val`+`test`) — модель не видела именно эти окна на обучении, даже если видела другие окна того же `rate` в train.

**Результат на реальном датасете** (те же 92+ запуска лаборатории, что и в разделах выше). Самое чёткое наблюдение: у Random Forest recall остаётся высоким почти на всех группах, где вообще есть отложенные данные (`syn_flood` 1.0/0.944 на 200/1000 pps, `slow_scan` 1.0, `slowloris` 1.0 на обеих интенсивностях, `dns_tunnel` 1.0 на 10 и 40 запросов/с) — в отличие от порогов и Isolation Forest, у которых recall куда более рвано зависит от конкретного сценария и `rate` (Isolation Forest, например, почти везде 0.0, кроме `dns_tunnel` и нескольких «громких» вариантов — то же самое ограничение контаминации 0.01, что и в разделе Isolation Forest выше, здесь просто видно ещё нагляднее). Есть и контринтуитивные строки — например, `port_scan` у Random Forest: recall 1.0 при `rate=500`, но 0.5 при `rate=1000` (более быстрое сканирование поймано хуже, не лучше) — и `c2_beacon` у порогов: 0.5 при `rate=1`, но 0.0 при `rate=5`.

**Ограничение честности, а не результата**: большинство `rate`-групп в отложенной выборке — это 2–18 строк (один-два прогона лаборатории на комбинацию сценарий+`rate`), а для части комбинаций (`syn_flood` на 5000 pps, например) все прогоны целиком попали в `train`, и в отложенной выборке эта интенсивность вообще отсутствует. На таком размере группы «recall упал с 1.0 до 0.5» и «recall упал с 1.0 до 0.0» неотличимы от шума одного-двух прогонов — контринтуитивные строки выше стоит читать как «требует больше прогонов для проверки», а не как надёжно установленный эффект. Настоящая проверка чувствительности к интенсивности потребовала бы отдельной кампании с несколькими повторами на каждый `rate` для каждого сценария, а не анализа уже существующих данных постфактум — это и есть логичное следующее действие, если чувствительность к интенсивности станет отдельным вопросом дальнейшей работы.

## Перенос на внешний датасет (M10)

```bash
uv run netstream-ml evaluate transfer data/v1 <cic-flowmeter>.csv --window 5
```

Все результаты выше проверяют одно и то же: обобщается ли модель на атаки, которых не видела *в обучении*, но всё ещё внутри одной и той же лаборатории — тот же eBPF-агент, тот же формат признаков, те же фоновые хосты. M10 — другой вопрос: что случится с тем же детектором на трафике совсем из другого источника, собранном другим инструментом (`netstream_ml.external`, датасеты CIC-IDS2017/CIC-DDoS2019).

CICFlowMeter — не наш агент: он агрегирует по одному потоку (5-tuple), а не по (`src_ip`, окно), и не заглядывает в полезную нагрузку DNS вообще. Из-за этого большая часть `FEATURE_COLUMNS` не восстанавливается из его CSV в принципе, а не потому что не хватило времени на парсинг:

- все `dns_*` — в датасете нет разбора DNS-запросов;
- `receive_ratio` — у нас это доля пакетов окна, адресованных источнику *извне* его собственных потоков; у CICFlowMeter fwd/bwd — это направление внутри одного и того же потока, другая ось;
- `synack_ratio` — нет отдельного счётчика SYN+ACK, только раздельные SYN/ACK;
- `aggregated_ratio` — GRO/GSO-агрегация пакетов существует только на уровне eBPF-агента;
- все `size_*_ratio` — CICFlowMeter даёt min/max/mean/std длины пакета на поток, а не гистограмму по отдельным пакетам, бины из этого не восстановить даже приближённо.

`RECONSTRUCTABLE_FEATURES` — то, что осталось (9 из 24): счётчики пакетов/байт/потоков, разброс по destination, `syn_ratio`/`rst_ratio`, среднее и стандартное отклонение межпакетного интервала (пересчитанные из **пер-потокового** mean/std тем же способом, каким `WindowAccumulator` объединяет статистику нескольких записей в одно окно — иначе усреднение по потокам внутри окна было бы смещённым). `evaluate transfer` переобучает все три baseline'а на лабораторных данных, урезанных до этого же подмножества, и оценивает на:

- `lab_test_same_features` — тот же тестовый сплит лаборатории, что и везде выше, но **только** на урезанном наборе признаков — чтобы отделить «цена урезания признаков» от «цена переноса на другой источник данных»;
- `external` — тот же обученный детектор на признаках, посчитанных из внешнего CSV.

**Результат на реальном датасете.** Внешний файл — `UDPLag.csv` из CIC-DDoS2019 (`01-12`, тренировочный день), самый маленький файл в архиве (1176 окон после агрегации: 645 `benign`, 426 `udp-lag`, 105 `webddos`). Падение резкое и по recall, и по precision у всех трёх baseline'ов:

| | lab test (урезанные признаки) | external |
|---|---|---|
| threshold | F1 0.603 (precision 0.636, recall 0.574) | F1 0.070 (precision 0.113, recall 0.051, **FPR 0.329**) |
| Isolation Forest | F1 0.063 (recall 0.033) | F1 0.033 (recall 0.017) |
| Random Forest | F1 0.949 (precision 0.982, recall 0.918) | F1 0.256 (precision 0.330, recall 0.209, **FPR 0.349**) |

Random Forest остаётся лучшим из трёх и на внешних данных, но падение с F1 0.949 до 0.256 — это не «немного хуже», а «почти не работает»: FPR 0.349 означает, что треть обычного фонового трафика чужой сети размечается как атака. По сценариям видно и почему: recall на `udp-lag` у леса — 0.204, на `webddos` — 0.229, оба намного ниже, чем на любом сценарии из раздела «Чувствительность к интенсивности атаки» выше, даже на самых тихих его вариантах.

**Первая гипотеза (уточняется ниже вторым и третьим прогоном).** UDPLag — атака поверх UDP, у неё нет TCP-флагов, а 2 из 9 восстановимых признаков (`syn_ratio`, `rst_ratio`) на UDP-трафике тождественно равны нулю что для атаки, что для фона — правдоподобная (но, как окажется ниже, не полная) причина низкого recall. Высокий FPR на `benign`-строках внешнего датасета — это, судя по всему, отдельный эффект: «нормальный» трафик другой сети (другие IP-диапазоны, другое распределение `unique_dst_ports`/`flows_count`) просто не похож на «нормальный» трафик лаборатории, на котором калибровались пороги. Это именно тот разрыв между «обобщение на новую атаку внутри своей же лаборатории» (M8: F1 0.983 на полном наборе признаков; M9: recall 0.9–1.0 почти на всех rate-группах Random Forest) и «перенос на чужую сеть и чужой инструмент сбора» — второе оказалось на порядок сложнее, и один прогон на одном файле уже это ясно показывает.

**Проверка гипотезы: второй прогон, `Syn.csv` (TCP SYN-flood, тот же день CIC-DDoS2019).** Всего 179 окон после агрегации (87 `benign`, 92 `syn`) — заметно меньше, чем на `UDPLag.csv`, потому что почти весь поток шёл от одного-двух атакующих адресов; читать эти числа стоит с той же осторожностью, что и малые `rate`-группы в разделе M9 выше.

| | external (UDPLag, UDP) | external (Syn, TCP) |
|---|---|---|
| threshold | F1 0.070 (recall 0.051, FPR 0.329) | F1 0.568 (recall 0.522, FPR 0.333) |
| Isolation Forest | F1 0.033 (recall 0.017) | F1 0.467 (recall 0.304) |
| Random Forest | F1 0.256 (recall 0.209, FPR 0.349) | F1 0.543 (recall 0.511, FPR 0.391) |

Recall всех трёх baseline'ов на TCP-атаке в 3–10 раз выше, чем на UDP-атаке (Isolation Forest — 0.304 против 0.017), что на первый взгляд подтверждает гипотезу про `syn_ratio`. При этом FPR на `benign`-окнах остался почти таким же высоким (0.33–0.39 против 0.33–0.35 на UDPLag) — то есть ложные срабатывания на фоновом трафике чужой сети объясняются не спецификой атаки, а именно тем, что «нормальный» трафик внешней сети не похож на «нормальный» трафик лаборатории. Возможность детектировать атаку и умение не путать чужой benign со своим — это два разных провала, и перенос признаков лечит только первый.

**Третий прогон, `DrDoS_LDAP.csv` (UDP-amplification, тот же день).** 636 окон (398 `benign`, 238 `drdos_ldap`) — этот прогон опровергает исходную формулировку гипотезы «дело в протоколе»:

| | UDPLag (UDP, «тихая» атака) | Syn (TCP-flood) | DrDoS_LDAP (UDP-amplification) |
|---|---|---|---|
| threshold | F1 0.070 (recall 0.051) | F1 0.568 (recall 0.522) | F1 0.541 (recall 0.508) |
| Isolation Forest | F1 0.033 (recall 0.017) | F1 0.467 (recall 0.304) | F1 0.667 (recall 0.500) |
| Random Forest | F1 0.256 (recall 0.209) | F1 0.543 (recall 0.511) | F1 0.498 (recall 0.483) |

`DrDoS_LDAP` — тоже UDP-атака (без единого TCP-флага в трафике), но её recall не просто выше, чем у `Syn`, а местами лучший из трёх (Isolation Forest — 0.500 против 0.304 на TCP). Значит `syn_ratio` — не главная причина провала на `UDPLag`: реальная переменная — насколько объёмна атака сама по себе. `Syn` и `DrDoS_LDAP` — это заливка (много пакетов/байт, экстремальные `unique_dst_ports` или `payload_bytes_total` в окне), их видно по оставшимся 7 признакам почти так же хорошо, как и по 9; `UDPLag` — это низкообъёмная атака на задержку соединения, которая не выделяется по объёму вообще, и именно поэтому она — а не «UDP vs TCP» — оказалась тем конкретным случаем, где урезанный набор признаков ловит атаку хуже всего.

**Ограничение честности.** Все три прогона — один датасет (CIC-DDoS2019, день `01-12`); FPR на `benign`-окнах чужой сети во всех трёх — 0.22–0.39, стабильно высокий независимо от типа атаки, что и является главным систематическим выводом M10, а не отличие между атаками. CIC-IDS2017 (другой год, датасет с не-DDoS сценариями вроде брутфорса и инфильтрации) и остальные файлы CIC-DDoS2019 пока не проверялись.

## Смещение между эмуляцией и настоящим инструментом (M11)

M9 и M10 проверяют устойчивость к перемене интенсивности и переносу на чужую сеть. Третий вид дрейфа — более узкий, но внутри самого `dns_tunnel`: лаборатория размечает два сценария одной и той же меткой (`label = dns_tunnel`), но разным `scenario` — `dns_tunnel` (`lab/dns_tunnel.py`, эмуляция запросами по расписанию) и `iodine_tunnel` (настоящий `iodine` через контейнер `tunnel`, реальная передача данных через `dns0`). Раз оба попадают в одну выборку как один класс атаки, стоит явно проверить, не переобучается ли модель только на особенностях эмуляции, упуская то, чем настоящий туннель отличается на практике — то, на что README лаборатории раньше только намекал («для проверки на смещение стоит использовать оба»), без отдельного прогона и цифр.

**Прогон.** 4 запуска `dns_tunnel` (`rate=20`, `qtype=mixed`, `duration=20`) и 4 запуска `iodine_tunnel` (`duration=25`) в одной лабораторной сессии, та же выгрузка и то же разбиение (`--seed 0`), что и везде выше — `scenario` у обоих сценариев уже отдельная колонка в `labeled_flows`/`labeled_dns`, то есть `evaluate_baseline_by_scenario` (используется во всех `baseline_*_w5.json` выше) и без того считает recall по каждому из них отдельно; M11 — не новый код, а то, что эти два числа ещё никто не сравнил напрямую.

**Результат.** Recall на test-сплите (1 запуск каждого сценария — именно так распределяют 4 запуска сплит-пропорции 0.6/0.2/0.2, см. оговорку ниже):

| Baseline | `dns_tunnel` (эмуляция) | `iodine_tunnel` (настоящий) |
|---|---|---|
| threshold | recall 1.000 (precision 1.000) | recall 0.842 (precision 1.000) |
| Isolation Forest | recall 1.000 | recall 1.000 |
| Random Forest | recall 1.000 | recall 1.000 |
| Gradient Boosting | recall 1.000 | recall 1.000 |

Единственный заметный разрыв — у порогового baseline (0.842 против 1.000): остальные три модели, обученные сразу на обоих сценариях совместно (а не отдельно на каждом), ловят настоящий туннель так же хорошо, как эмуляцию — в этом датасете разница между эмуляцией и реальным инструментом не стала системной проблемой ни для одной модели с учителем или ансамблем, только для самого простого детектора.

**Почему порог всё-таки промахивается на части окон `iodine_tunnel`, а не на `dns_tunnel`.** Сравнение признаков между сценариями показывает, чем они реально отличаются: `dns_entropy_mean` у эмуляции выше (4.53 против 3.31 у `iodine`) — то есть по энтропии имён настоящий туннель выглядит даже спокойнее эмуляции, не тревожнее; зато `packets_total` на окно у `iodine` в среднем **3261** против **80** у эмуляции — настоящий туннель на порядки объёмнее, потому что реально передаёт данные через `dns0`, а не просто шлёт запросы по расписанию. Пороговый baseline не содержит правила по абсолютному объёму трафика для DNS-сценариев (`packets_total` в его списке признаков калибруется по общему, не DNS-специфичному квантилю) — и именно поэтому часть низкоактивных окон `iodine_tunnel` (вероятно, фаза установления сессии) проходит мимо, тогда как Random Forest/Gradient Boosting, обучаясь на полном наборе признаков сразу, подхватывают этот объёмный сигнал без явного правила под него.

**Ограничение честности.** 4 запуска на сценарий — это тест-сплит из одного запуска на сторону, то же ограничение малой выборки, что в M9: единственный плохой (или редкий) запуск `iodine_tunnel` неотличим от систематической слабости на таком размере, а recall 1.000 у трёх из четырёх baseline'ов на обоих сценариях может означать как «модель действительно не видит разницы», так и «эта конкретная лабораторная сессия оказалась слишком лёгкой для обоих сценариев». Настоящая проверка смещения требует кампании с несколькими независимыми сессиями (не только несколькими запусками подряд в одной), как и в М9 выше.

## Отслеживание экспериментов (MLflow)

Каждый запуск `baseline threshold`/`baseline isolation-forest`/`baseline random-forest`/`evaluate compare` дополнительно логируется в MLflow: параметры запуска (окно, `target_fpr`/`contamination`, подобранные гиперпараметры), метрики по каждому сплиту и сам JSON-отчёт как артефакт. По умолчанию — локально, без какой-либо инфраструктуры (файл/база в текущей директории), эксперимент называется `netstream-baselines`.

```bash
uv run netstream-ml baseline threshold data/v1 --window 5
uv run mlflow ui   # http://127.0.0.1:5000 — сравнение прогонов таблицей и графиками
```

Смысл — не заменить JSON-отчёты (они остаются источником правды для README и скриптов), а дать быстрый способ визуально сравнить релизы модели друг с другом, не открывая файлы вручную: несколько прогонов `baseline random-forest` с разными сидами/гиперпараметрами сразу видны рядом в таблице MLflow UI с сортировкой по метрике.

Точка подключения — `MLFLOW_TRACKING_URI` (тот же принцип переопределения, что и у `CLICKHOUSE_URL`): если её нет, MLflow пишет в `./mlruns`/`mlflow.db` рядом с текущей директорией (в `.gitignore`, не коммитится); если она есть — данные идут на реальный MLflow-сервер (backend/deploy этот сервер пока не поднимают — это отдельная задача, если локальный вариант окажется полезным). Логирование никогда не роняет команду: если MLflow недоступен, в stderr печатается предупреждение, а сам отчёт всё равно считается и пишется как обычно.

## Онлайн-детектор (M16)

Всё выше — обучение и оценка offline, на выгрузке из ClickHouse. `netstream_ml.detector` — реальный онлайн-цикл: читает те же OTLP-логи (`netstream.events.v1`), что и `otel-gateway` для заполнения ClickHouse, но на отдельной consumer group, так что ни один из путей не влияет на другой (`docs/architecture/system.md`, «Целевая архитектура»). Каждое сообщение разбирается в `netstream_ml.otlp_decode`, кормит `features.WindowAccumulator` — тот же инкрементальный накопитель, который `tests/test_features_parity.py` уже сверяет с батчевым `build_features` — и завершённые окна оцениваются baseline-моделью, обученной offline любой из команд `baseline` выше.

На каждый `host_id` — свой `WindowAccumulator`, а не один общий: накопитель ключует окна только по `src_ip`, а два разных сенсора могут легитимно видеть перекрывающиеся приватные диапазоны адресов (разные площадки, разные VLAN) — общий накопитель на всех сенсоров незаметно слил бы их окна.

### Надёжность: ручной commit, идемпотентный producer, дедупликация детекций

`confluent_kafka.Consumer` по умолчанию коммитит офсеты сам, по таймеру (`enable.auto.commit`) — независимо от того, успела ли публикация детекции того же сообщения реально дойти до брокера. Падение детектора между «офсет закоммичен» и «`producer.produce()` реально подтверждён» тихо теряло бы детекцию без единого следа. `run_kafka_detector` коммитит входной офсет вручную (`enable.auto.commit=False`, `consumer.commit(message=msg, asynchronous=False)`) и только после того, как `producer.flush()` подтвердил через delivery callback каждого произведённого сообщения, что оно реально дошло до брокера (`_produce_detections`); если хоть одно сообщение не подтвердилось за `--produce-timeout-seconds`, офсет для этого входного сообщения не коммитится вообще — следующий `poll()` для этой consumer-группы отдаст его снова. `producer` поднят с `enable.idempotence=True`, чтобы ретрай самого `produce()` после временной ошибки брокера не создал дубликат на стороне брокера.

От повторной обработки одного и того же окна после падения между публикацией и коммитом это не защищает — это в принципе невозможно без двухфазного коммита между Kafka-топиками. Вместо этого каждая публикуемая детекция несёт стабильный Kafka-ключ `_detection_key` — `f"{host_id}:{src_ip}:{window_start}:{window_seconds}"` — не зависящий от того, сколько раз это окно переобработано и переопубликовано; получатель `netstream.detections.v1`, которому важна идемпотентность (например, materialized view в ClickHouse), может дедуплицировать по этому ключу вместо предположения «одно сообщение — одно окно».

Отдельно: `flush()` может закрыть окно, которому не досталось нового входного сообщения (источник затих) — на этот случай раз в `--idle-flush-seconds`, а также при остановке, детектор зовёт `consumer.commit(asynchronous=False)` без явного `message=`. Такой «голый» commit коммитит то, что уже было сохранено этим же consumer-хендлом с прошлого коммита — а поскольку офсеты сохраняются только явными коммитами по конкретному сообщению, к моменту idle-flush обычно сохранять уже нечего. `confluent_kafka` в этом случае не возвращает «нечего коммитить» как успех, а кидает `KafkaException` с кодом `_NO_OFFSET` — без защиты это реально роняет процесс детектора (воспроизведено на реальном Kafka-брокере: после обработки входных сообщений и последующего пустого idle-flush/shutdown процесс падал с `cimpl.KafkaException: KafkaError{code=_NO_OFFSET,...}`). `_commit_if_anything_to_commit` ловит именно этот код и молча пропускает, пробрасывая любую другую ошибку коммита как есть.

Проверено на реальном Kafka (одноброкерный docker-контейнер из `deploy/compose.yml`, без моков): опубликованы два настоящих OTLP-батча (`ExportLogsServiceRequest`) в `netstream.events.v1`, `detect run`-эквивалент (`run_kafka_detector` напрямую, с `--max-messages 2`) реально закрыл окно, опубликовал детекцию в `netstream.detections.v1` с корректным ключом `sensor-real-1:10.0.0.50:1700000010:5` и успешно завершился; `kafka-consumer-groups --describe` после завершения показал `LAG=0` на всех партициях `netstream.events.v1` (офсеты реально закоммичены), а `kafka-console-consumer` реально прочитал опубликованную детекцию из топика. До фикса `_commit_if_anything_to_commit` тот же сценарий детерминированно падал на idle-flush/shutdown коммите.

### Сохранение и регистрация модели (M14)

Любой из четырёх `baseline`-команд (`threshold`, `isolation-forest`, `random-forest`, `gradient-boosting`) умеет дополнительно сохранить обученную модель локально (`joblib.dump` в её исходном виде — детектор зависит только от общего протокола `.predict(frame)`/`.decision_score(frame)`, который уже реализуют все четыре baseline'а, а не от конкретного класса модели):

```bash
uv run netstream-ml baseline random-forest data/v1 --window 5 --save-model artifacts/model.joblib
```

Чтобы `detect run` мог взять эту модель без локального файла на диске (например, запущенный в отдельном контейнере/хосте), `--save-model` можно дополнить регистрацией в реестре моделей `backend` (`internal/models`, артефакт лежит в S3-совместимом `objectstore`, сам backend никогда не проксирует байты — отдаёт 302 на presigned URL):

```bash
openssl genpkey -algorithm ed25519 -out signing_key.pem
openssl pkey -in signing_key.pem -pubout -out verify_key.pem

uv run netstream-ml baseline random-forest data/v1 --window 5 \
    --save-model artifacts/model.joblib \
    --register-model random-forest --model-version 2026-10-18 \
    --signing-key signing_key.pem \
    --backend-url http://127.0.0.1:9999
```

`--register-model` требует `--save-model` (откуда берутся байты), `--model-version` (у backend нет отдельного алиаса "latest" — версии различаются только явной строкой, обычно датой или git SHA) и `--signing-key` (Ed25519 приватный ключ, PEM) — без любого из трёх команда возвращает ошибку и ничего не публикует.

`--signing-key` — не формальность: `joblib.load()` на произвольных байтах выполняет произвольный код при десериализации, а объектное хранилище и сам backend — не доверенная граница сама по себе (ровно в этом и состоял P0 из внешнего ревью безопасности). `upload_artifact` считает `sha256` байт артефакта и подписывает его `--signing-key` (Ed25519, `netstream_ml.model_registry.sign_artifact`), оба значения уходят в заголовках `X-Artifact-Sha256`/`X-Artifact-Signature` и backend сохраняет их как есть — backend не умеет их проверять, у него нет и не будет приватного ключа, он только хранит то, что заявил публикующий. `detect run --model-name` (и прямой вызов `load_model`) требуют `--verify-key` (Ed25519 публичный ключ) и отказываются грузить артефакт, если `sha256` не совпадает или подпись не проходит — до `joblib.load`, не после.

Проверено на реальном стенде (реальный `backend` на Postgres + SeaweedFS, настоящая пара ключей Ed25519): `baseline random-forest --save-model --register-model --signing-key` реально регистрирует модель, заливает артефакт и возвращает настоящие `sha256`/подпись в `GET /api/v1/models/...`; `load_model` с правильным `--verify-key` реально скачивает артефакт через presigned-редирект, проверяет подпись и разворачивает `joblib.load`; с чужим публичным ключом или с подменёнными байтами (имитация скомпрометированного объектного хранилища) — реальный, не смоделированный отказ до `joblib.load`. Модель без `artifact_sha256`/`artifact_signature` в реестре (загруженная до этой фичи, или без `--signing-key`) тоже не загружается — отсутствие подписи не трактуется как «доверять по умолчанию».

### Экспорт в ONNX

`--export-onnx PATH` на любой из четырёх `baseline`-команд конвертирует только что обученную модель в ONNX и пишет файл:

```bash
uv run netstream-ml baseline random-forest data/v1 --window 5 --export-onnx artifacts/model.onnx
```

Три из четырёх baseline оборачивают scikit-learn/XGBoost-оценщик и конвертируются существующими библиотеками (`skl2onnx` для Isolation Forest и Random Forest, `onnxmltools` для XGBoost). У `ThresholdBaseline` оценщика нет вообще — это набор сравнений по признакам, — поэтому её граф собирается руками через `onnx.helper`: `Greater`/`Less` и вычисление нормализованного превышения на каждое правило, `Or`-свёртка для `predict`, max-свёртка для `decision_score`. Реализация и диспетчеризация по типу — `netstream_ml.onnx_export`.

Перед тем как записать файл, команда прогоняет экспортированную ONNX-модель на test-сплите через `onnxruntime` и сравнивает `predict`/`decision_score` с оригиналом (`np.array_equal`/`np.allclose`, `atol=1e-4` — разница float32 ONNX-графа от float64 polars/sklearn); при несовпадении файл не пишется, команда возвращает код 1 с понятным сообщением, а не тихо отдаёт неверный ONNX. Так же устроены `tests/test_onnx_export.py`: каждый из четырёх типов обучается на синтетических данных, конвертируется и сверяется с оригиналом поштучно.

Экспортированная модель принимает один тензор `input` формы `(batch, N)` — `to_onnx()` возвращает вместе с моделью `feature_order`, точный порядок колонок, которого эта модель ожидает (у ONNX-графов нет имён колонок — перепутать порядок значит тихо получить неверные предсказания). У трёх оценщик-моделей порядок — это `baseline.features`; у `ThresholdBaseline` — порядок первого упоминания признака среди её правил.

Экспортированная модель самодостаточна: `to_onnx()` записывает `feature_order` и тип baseline (`kind`) прямо в `metadata_props` файла — `.onnx` с диска можно загрузить обратно и сразу использовать, без отдельного sidecar-файла с метаданными (см. `detect run --onnx-model` ниже).

**Что здесь не сделано.** `--export-onnx` — отдельный путь от `--save-model`/`--register-model`: экспортированный `.onnx`-файл никуда не публикуется (ни в реестр моделей `backend`, ни в объектное хранилище), это просто локальный файл. `detect run --onnx-model` (ниже) умеет его читать, но по-прежнему только с диска — связать ONNX с реестром моделей (регистрация/скачивание `.onnx`-артефактов тем же путём, что и `.joblib`) пока не сделано.

### `detect run`

```bash
uv run netstream-ml detect run \
    --model-name random-forest \
    --verify-key verify_key.pem \
    --window 5 \
    --bootstrap-servers localhost:9092 \
    --events-topic netstream.events.v1 \
    --detections-topic netstream.detections.v1 \
    --consumer-group netstream-detector \
    --idle-flush-seconds 30
```

Ровно один из `--model-name` (реестр `backend`) или `--onnx-model PATH` (локальный файл от `--export-onnx` выше) обязателен — ни тот, ни другой по умолчанию, оба сразу или ни одного — явная ошибка:

```bash
uv run netstream-ml detect run --onnx-model artifacts/model.onnx --window 5 --bootstrap-servers localhost:9092
```

`--onnx-model` разворачивает файл через `onnxruntime.InferenceSession` один раз при старте (`OnnxBaseline` в `netstream_ml.onnx_export` — реализует тот же протокол `Baseline`, что и `joblib`-модели, так что `OnlineDetector` не видит разницы) и дальше работает как обычно, без обращения к `backend` вообще. `--model-name` обязателен для пути через реестр, вместе с `--verify-key` (Ed25519 публичный ключ — см. «Сохранение и регистрация модели (M14)» выше; без него команда отказывается стартовать, а не грузит модель без проверки); `--model-version` по умолчанию берёт самую новую зарегистрированную версию этого имени (backend сортирует список по `(name, created_at DESC)`, так что первое совпадение по имени уже самое новое — отдельного алиаса для этого нет). `--backend-url` можно не указывать явно — он читается из `BACKEND_URL`. Остальные флаги можно задать переменными окружения вместо флагов: `KAFKA_BOOTSTRAP_SERVERS`, `KAFKA_EVENTS_TOPIC`, `KAFKA_DETECTIONS_TOPIC`, `KAFKA_CONSUMER_GROUP` — тот же принцип, что и у `CLICKHOUSE_URL` для offline-команд.

Консюмер читает `--events-topic`, декодирует OTLP-батч, кормит окна в накопитель своего `host_id` и для каждого закрывшегося окна считает `score`/`is_attack` обученной моделью, публикует результат в `--detections-topic` и пишет его в лог, если это атака. Окно, не получившее более позднюю запись того же источника (источник ушёл в тишину), иначе осталось бы открытым навсегда — поэтому раз в `--idle-flush-seconds` детектор принудительно закрывает (`flush`) все ещё открытые окна по всем сенсорам, а также один раз при остановке. При завершении печатает p50/p95 задержки по всем сделанным детекциям.

Логирование настраивается самим `detect run` (`logging.basicConfig(level=logging.INFO)`) — без этого `logger.info` (лог каждой детекции, финальная сводка p50/p95) молча проглатывается стандартным уровнем root-логгера (`WARNING`) и не появляется в stdout, хотя детекции при этом всё равно реально пишутся в Kafka. Это было проверено на реальном стенде: без `basicConfig` процесс завершался с кодом 0 и ни строчки лога, при этом сами детекции читались из `netstream.detections.v1` напрямую.

### Формат `DetectionResult`

Каждая публикация в `--detections-topic` — JSON-объект:

```json
{
    "host_id": "sensor-1",
    "src_ip": "10.0.0.5",
    "window_start": 1700000000,
    "window_seconds": 5,
    "score": 11.5,
    "is_attack": true,
    "latency_ms": 842.3
}
```

`window_start` — unix-время (секунды) начала окна. `score` — не нормализованная вероятность, а `decision_score` конкретной модели (для `threshold` — наибольшее превышение порога, для `isolation-forest` — инвертированная `decision_function`, для `random-forest` — вероятность класса «атака»); сравнивать `score` между разными моделями напрямую нельзя. `latency_ms` — сколько времени прошло между теоретическим концом окна (`window_start + window_seconds`) и моментом, когда детектор его оценил.

**`latency_ms` может быть отрицательным** — это не ошибка. В обычной работе окно закрывается, когда приходит более поздняя запись того же источника: это происходит уже после теоретического конца окна, и `latency_ms` положительна (сколько реально заняла доставка плюс обработка). Но принудительный `flush()` — по `--idle-flush-seconds` или при остановке процесса (например, `--max-messages`) — закрывает окно прямо сейчас, независимо от того, наступил ли уже `window_start + window_seconds` по настенным часам: если `flush` сработал до теоретического конца окна, `latency_ms` выходит отрицательной. Проверено на реальном стенде (`-730.1ms` при `flush()` сразу после единственного события, настроенном `--max-messages 1`) — это честный сигнал «окно закрыто принудительно, раньше срока», а не причина обрезать значение до нуля.
