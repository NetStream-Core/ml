# NetStream ML

Датасеты, признаки, модели и оценка для детектора сетевых атак NetStream. Данные берутся из ClickHouse стека `deploy` (размеченные представления `labeled_flows` и `labeled_dns`), обученные модели используются онлайн-детектором.

## Состав

| Путь | Назначение |
|---|---|
| `src/netstream_ml/` | пакет и CLI `netstream-ml` |
| `tests/` | тесты |
| `data/` | выгрузки датасетов (не в git) |
| `artifacts/` | модели и отчёты (не в git) |

## Разработка

Нужны Python 3.12+ и [`uv`](https://docs.astral.sh/uv/).

```bash
uv sync
uv run pytest
just all
```

- `just format` форматирует и правит `ruff`.
- `just lint` запускает `ruff`, проверку форматирования и `mypy --strict`.
- `just test` запускает `pytest`.

## Выгрузка датасета

Нужен запущенный стек `deploy` (`just up` или лаборатория `just lab-up`/`just lab-campaign`) с доступным HTTP-интерфейсом ClickHouse.

```bash
uv run netstream-ml data export data/v1 \
    --url http://127.0.0.1:8123 \
    --campaign-manifest ../deploy/lab/campaigns/manifests/v1-<timestamp>.json
```

Подключение можно задать переменными окружения `CLICKHOUSE_URL`, `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD`, `CLICKHOUSE_DATABASE` вместо флагов.

`labeled_flows` и `labeled_dns` — представления, которые для каждой строки перебирают все окна из `labels`, поэтому на датасете с полсотней запусков и сотней тысяч потоков запрос может упереться в лимит памяти ClickHouse по умолчанию. `data export` сам поднимает `max_memory_usage` до 2 ГиБ (`--max-memory-usage` или `CLICKHOUSE_MAX_MEMORY_USAGE`); если и этого не хватает, поднимать дальше или выносить разметку в материализованную таблицу — отдельная задача для `deploy`.

Команда выгружает `labeled_flows`, `labeled_dns` и `labels` в `flows.parquet`, `dns.parquet` и `labels.parquet` (ClickHouse отдаёт Parquet сам через `FORMAT Parquet`, без промежуточной конвертации) и пишет `manifest.json`: версия `netstream-ml`, версия сервера ClickHouse, список сценариев, число строк и sha256 каждого файла. С `--campaign-manifest` в манифест выгрузки попадает содержимое манифеста кампании (`deploy/lab/campaign.py`) целиком, с его собственной контрольной суммой — так выгрузка прослеживается до конкретного прогона лаборатории, включая git-ревизию агента.

## Разбиение на выборки

```bash
uv run netstream-ml data split data/v1 --seed 0 --train 0.6 --val 0.2 --test 0.2
```

Команда читает `labels.parquet`, `flows.parquet` и `dns.parquet` из указанной директории (результат `data export`), добавляет колонку `split` (`train`/`val`/`test`) в `flows.parquet` и `dns.parquet` и пишет `split_manifest.json`.

Единица разбиения — запуск сценария (`run_id`), а не отдельная запись: все записи одного запуска атаки или доброкачественного профиля целиком уходят в одну выборку, чтобы модель не видела один и тот же инцидент и при обучении, и при проверке. Сценарий с тремя и более запусками представлен во всех трёх выборках (наибольший остаток, детерминированный порядок по seed); сценарий с одним-двумя запусками может не попасть в тест или в валидацию — это ограничение малой лаборатории, а не ошибка.

У фонового трафика (`scenario = background`, нет `run_id`) нет привязки к запуску — он идёт постоянно между сценариями. Такие записи группируются по 30-секундным интервалам времени, и каждый интервал целиком уходит в одну выборку. Это уменьшает, но не убирает утечку: фоновый поток, чей интервал съёма пересекает границу 30-секундного окна, может отдать часть своих записей в разные выборки.

Разбиение детерминировано (`--seed`): одинаковый seed на одном датасете даёт одинаковое разбиение, что нужно для воспроизводимости экспериментов. `split_manifest.json` фиксирует seed, доли выборок, разбиение по `run_id` и отчёт о проверке утечек (`check_run_leakage`) для `flows` и `dns`; команда возвращает код выхода `1`, если хоть один `run_id` оказался больше чем в одной выборке.

**Важно про порядок команд**: `features build` наследует колонку `split` из `flows.parquet`/`dns.parquet`, если она уже там есть (тем же правилом «последняя запись в окне», что и для `label`/`scenario`). Разбивать нужно **до** построения признаков — тогда у каждой строки признаков будет своя выборка и повторно считать признаки на train/val/test отдельно не придётся. Если `data split` не запускали, `features build` просто не добавит колонку `split`.

## Признаки

```bash
uv run netstream-ml features build data/v1 --window 1 --window 5 --window 10
```

Читает `flows.parquet` и `dns.parquet` из директории выгрузки, считает признаки за скользящее по эпохе окно (по умолчанию 1, 5 и 10 секунд, флаг можно повторять) отдельно для каждого источника (`src_ip`) и пишет `features_w<N>.parquet` плюс `features_manifest.json` с числом строк по каждому окну.

Единица агрегации — источник за окно, а не отдельный поток: одна строка описывает, чем в данный момент занят конкретный хост (объём трафика, доля SYN/SYN-ACK/RST, доля пакетов, попавших в агрегированные записи агента при флуде, распределение по размеру пакетов, статистика межпакетных интервалов, число уникальных адресов и портов назначения; со стороны DNS — число запросов, длина и энтропия имён, доля TXT/NULL, доля запросов по TCP, максимум уникальных поддоменов). Метка и сценарий окна берутся из последней по времени записи в нём.

Расчёт живёт в `netstream_ml.features` как две реализации одной спецификации: `build_features` — быстрый батч на polars для обучения моделей, `WindowAccumulator` — простой инкрементальный накопитель для будущего онлайн-детектора (M16), который можно кормить записями по одной по мере поступления из Kafka. `tests/test_features_parity.py` прогоняет одни и те же сгенерированные данные через обе реализации и сверяет результат с точностью до `1e-9` — иначе легко незаметно разойтись и получить skew между обучением и продакшеном.

**Ограничения.** Окно короче, чем интервал съёма агента (`REPORT_INTERVAL_MS`, по умолчанию 1 с), не даст дополнительной гранулярности — запись потока уже агрегирована на уровне агента. Источник без DNS-активности в окне получает нулевые счётчики и `null` в средних/максимумах (там нечего усреднять). В лаборатории атакующий и обычный клиент — разные адреса, поэтому смешение меток внутри одного окна возможно только на границе запуска сценария. `synack_ratio` считается внутри окна одного источника и показывает долю его собственных SYN-пакетов, которые сами являются SYN-ACK (то есть источник отвечает на чужие подключения, а не проверку «дошли ли ответы на мои SYN»): ответ на SYN приходит от другого адреса и попадает в окно этого другого адреса, поэтому у атакующего источника `synack_ratio` почти всегда 0 — это ожидаемо, не признак того, что флуд не долетел до жертвы.

Проверено на реальном датасете (92 запуска лаборатории, 254 080 потоков, 105 812 DNS-записей после экспорта): `aggregated_ratio` у `syn_flood` в среднем 0.69 против 0.01 у `benign` (бюджет новых потоков агента исчерпывается именно на флуде, как и задумано), `dns_entropy_mean` у `dns_tunnel` — 3.96 против 3.19 у фонового трафика.

## Baseline: пороговые правила

```bash
uv run netstream-ml baseline threshold data/v1 --window 5 --target-fpr 0.01
```

Для каждого признака из фиксированного списка (`aggregated_ratio`, `unique_dst_ports`, `packets_total`, `rst_ratio`, `syn_ratio`, `dns_txt_null_ratio`, `dns_entropy_mean`, `dns_unique_subdomains_max`) берётся квантиль `1 - target_fpr` его значений на доброкачественных строках **обучающей** выборки — порог, на котором этот признак сам по себе ложно сработал бы примерно на `target_fpr` доли benign-трафика. Правила объединяются через ИЛИ: сработало любое — окно помечено как атака. Никакого обучения, кроме чтения квантиля: это самый простой детектор, с которым нужно сравнивать любую модель, — если случайный лес не обгонит его с заметным запасом, лес не оправдывает сложность.

Команда требует, чтобы `features_w<N>.parquet` уже содержал колонку `split` (то есть `data split` был запущен до `features build`), считает метрики (precision, recall, F1, FPR, accuracy) на train/val/test и отдельно по каждому сценарию на test, пишет `baseline_threshold_w<N>.json`.

**Результат на реальном датасете** (92 запуска, окно 5 с): F1 = 0.66 на test, без переобучения (train/val/test близки — 0.663/0.667/0.661), что подтверждает: разбиение по `run_id` действительно не даёт утечки. По сценариям: `syn_flood`, `slow_scan`, `port_scan`, `dns_tunnel` (эмуляция) — recall 1.0, простые пороги их ловят полностью. `c2_beacon` (recall 0.33), `iodine_tunnel` (0.50), `slowloris` (0.29) — медленные и низкоскоростные атаки пороги почти не видят, это ожидаемо и ровно то, ради чего нужны модели (M6–M7). Ложные срабатывания сосредоточены на «трудных» доброкачественных профилях: `admin_scan` (FPR 1.0 — неотличим от `port_scan` по признакам потока, известное ограничение), `reputation_dns`, `backup`, `web_burst`, `cdn_dns` — то есть профили D3 действительно стресс-тестируют детектор, а не остаются недостижимым фоном.
